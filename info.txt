# RustRE Suite — Documento di Implementazione Completo

> Specifica tecnica integrale per la costruzione di una piattaforma di reverse engineering interamente in Rust, con frontend GPUI, capace di replicare l'intero ecosistema di tool descritto: analisi statica, debugging, decompilation, time-travel, instrumentation, hex editing, diffing, fuzzing, deobfuscation, malware sandboxing, memory forensics, mobile reversing, .NET, emulation, symbolic execution, threat intelligence, e orchestrazione MCP/AI agent.

---

## 0. Premessa e correzione delle affermazioni precedenti

Va detto onestamente all'inizio del documento, perché determina come va affrontato il lavoro: **tutti gli algoritmi descritti in questo documento sono basati su materiale pubblico**. Non c'è stregoneria proprietaria che impedisce la replica. In particolare:

- **Decompilation theory**: la base è la tesi di Cristina Cifuentes (1994) "Reverse Compilation Techniques"; il Phoenix decompiler di Schwartz et al. (USENIX Security 2013); il paper DREAM "No More Gotos" di Yakdan et al. (NDSS 2015); il successivo "A Comb for Decompiled C Code" (AsiaCCS 2020); la serie "30 Years of Decompilation" di mahaloz.re (2024). Reko Decompiler è open source e implementa molte di queste tecniche. Ghidra decompiler è open source (Apache 2.0).

- **BinDiff**: pubblicato come open source da Google (Apache 2.0). I paper fondanti sono Halvar Flake "Structural Comparison of Executable Objects" (DIMVA 2004) e Dullien & Rolles "Graph-Based Comparison of Executable Objects" (SSTIC 2005). Miglioramento via Hungarian algorithm in BinSlayer.

- **TTD / Record-Replay**: il framework Nirvana è descritto in Bhansali et al. "Framework for instruction-level tracing and analysis of program executions" (VEE 2006). L'implementazione open source di riferimento è `rr` di Mozilla. PANDA platform fa rr-style sopra QEMU. Esistono paper successivi (iDNA, ReVirt, ARNOLD).

- **FLIRT**: descritto nell'articolo ufficiale Hex-Rays "FLIRT Technology In-Depth" e in vari blog post (Tim Strazzere, FireEye). L'algoritmo si basa su pattern di prologue/epilogue + variable bytes + CRC16 di porzioni stabili.

- **Frida**: completamente open source (frida-core, frida-gum). L'arms race con anti-detection è un problema continuo ma il codice base è studiabile.

- **Hex-Rays decompiler 1:1**: questo resta l'unico componente che, anche con tutta la teoria pubblica, richiede anni di tuning empirico per matchare la qualità di output di Hex-Rays su binari reali ottimizzati. Ma una qualità "Ghidra-level" o "DREAM-level" è raggiungibile.

L'unica cosa onesta che resta da dire è che la **manutenzione continua** (Frida vs nuovi iOS, decompiler vs nuovi compiler optimization, anti-debug vs nuove protezioni commerciali) è dove la maggior parte del lavoro si concentra nel tempo. Ma per il documento di implementazione, non è un blocco.

## 1. Architettura generale

### 1.1 Principi non negoziabili

Cinque decisioni architetturali determinano se il progetto cresce o muore:

**P1 — Plugin everywhere**. Nel core ci sono solo trait. Loader, Architecture, Decompiler, Debugger, AnalysisPass, FormatParser, Demangler, TypeSystem, ScriptEngine, Visualizer sono trait. Il loader PE è un plugin, esattamente come il loader Lua bytecode è un plugin. Zero conoscenza di formati hardcoded nel core. Questo è il pattern di Ghidra (`Loader`/`Processor`/`Analyzer`) e Binary Ninja (`BinaryView`/`Architecture`).

**P2 — IR multi-livello**. Tre layer di intermediate representation: LLIL (1:1 con asm ma normalizzato), MLIL (SSA, variabili al posto di registri, calling conventions risolte), HLIL (control flow strutturato, espressioni nidificate, pronto per pseudocode). Ogni analisi seria lavora su IR, non su asm. Il decompiler ha come input HLIL.

**P3 — MemoryProvider abstraction**. Un solo trait centrale astrae da dove vengono i bytes: file su disco (statico), processo attached (dinamico), emulator state (Unicorn-style), trace replay (TTD-style). Tutto il codice di analisi è agnostico rispetto alla fonte.

**P4 — Knowledge graph persistente**. Tutto lo stato analitico (simboli, funzioni, tipi, commenti, xref, struct definitions, patches, bookmarks, trace records) vive in un graph persistente SQLite-backed con event sourcing. Niente in-memory only.

**P5 — MCP-first**. Ogni capability esposta dal core è anche un endpoint MCP server. Un agente AI esterno (Claude, GPT, Qwen locale) può orchestrare l'intero tool via protocollo MCP. Questa è la differenza tra "ennesimo RE tool" e "RE platform agentic-native".

## 2. Core abstractions

Questo è il file più importante del progetto. Tutto si appoggia sopra. Va scritto bene una volta sola.

### 2.1 `rustre-core::address`

```rust
// Address è opaque, never bare u64
#[derive(Copy, Clone, PartialEq, Eq, PartialOrd, Ord, Hash, Debug)]
pub struct Address(pub u64);

impl Address {
    pub const NULL: Address = Address(0);
    pub fn offset(self, o: i64) -> Address {
        Address((self.0 as i64).wrapping_add(o) as u64)
    }
    pub fn align_up(self, align: u64) -> Address {
        Address((self.0 + align - 1) & !(align - 1))
    }
}

#[derive(Copy, Clone, Debug)]
pub struct AddressRange {
    pub start: Address,
    pub end: Address,
}

#[derive(Copy, Clone, PartialEq, Eq, Hash, Debug)]
pub enum AddressSpace {
    Default,      // virtual address space del binario
    Physical,     // physical memory (kernel/firmware)
    IOSpace,      // I/O ports
    Stack,        // thread-relative
    Heap,
    Register,     // r0..rN come "addresses" di registri
    Custom(u16),  // arch-specific (segment selectors, etc.)
}

#[derive(Copy, Clone, Debug)]
pub struct TypedAddress {
    pub address: Address,
    pub space: AddressSpace,
}
```

L'uso di tipo opaco per `Address` evita confusioni con `usize`/`u64` casuali e permette di cambiare implementazione in futuro (es. wide addresses per 128-bit/segmented).

### 2.3 `rustre-mem::memory_provider`

Il trait centrale. Tutto il codice di analisi e debug ci passa attraverso.

```rust
use async_trait::async_trait;

#[async_trait]
pub trait MemoryProvider: Send + Sync {
    /// Lettura sincrona di un range. Errore se non mappato.
    fn read(&self, addr: Address, len: usize) -> Result<Vec<u8>, MemError>;
    
    /// Scrittura sincrona. Errore se readonly o non mappato.
    fn write(&mut self, addr: Address, data: &[u8]) -> Result<(), MemError>;
    
    /// Regioni mappate al momento della query.
    fn regions(&self) -> Vec<MemoryRegion>;
    
    /// Se il provider rappresenta uno stato runtime modificabile (processo, emu).
    fn is_live(&self) -> bool { false }
    
    /// Per provider live: invalida cache, refresh regioni.
    async fn refresh(&mut self) -> Result<(), MemError> { Ok(()) }
    
    /// Snapshot per provider che lo supportano (TTD, emu).
    async fn snapshot(&mut self) -> Result<SnapshotId, MemError> {
        Err(MemError::Unsupported)
    }
    
    /// Restore a uno snapshot.
    async fn restore(&mut self, id: SnapshotId) -> Result<(), MemError> {
        Err(MemError::Unsupported)
    }
}

#[derive(Clone, Debug)]
pub struct MemoryRegion {
    pub range: AddressRange,
    pub perms: Permissions,
    pub name: Option<String>,
    pub source: RegionSource,
}

bitflags::bitflags! {
    pub struct Permissions: u8 {
        const READ    = 0b0000_0001;
        const WRITE   = 0b0000_0010;
        const EXECUTE = 0b0000_0100;
        const SHARED  = 0b0000_1000;
    }
}

#[derive(Clone, Debug)]
pub enum RegionSource {
    FileSection { file: PathBuf, section: String, file_offset: u64 },
    ProcessModule { module: String, pid: u32 },
    Anonymous,
    Heap, Stack,
    Emulated,
    Reconstructed,  // unpacked, allocated by analysis
}
```

Implementazioni concrete in `rustre-mem`:
- `FileMemoryProvider` — mmap di un binario su disco
- `ProcessMemoryProvider` — `ReadProcessMemory`/`process_vm_readv`/`mach_vm_read`
- `EmulatedMemoryProvider` — wrapper su Unicorn engine
- `TraceMemoryProvider` — replay TTD, restituisce lo stato a un tick
- `CompositeMemoryProvider` — overlay di N provider (utile per merge statico+dinamico)
- `PatchedMemoryProvider` — wrapper che applica una patch DB sopra un altro provider

### 2.4 `rustre-core::binary_view`

`BinaryView` è il "punto di ingresso" a un binario caricato. È sia un `MemoryProvider` sia il contenitore di tutta l'analisi associata.

```rust
pub struct BinaryView {
    pub id: ViewId,                              // unique per session
    pub uri: BinaryUri,                          // file path o "process:pid" etc.
    pub arch: ArchHandle,
    pub endian: Endian,
    pub bits: u8,                                // 16, 32, 64, 128
    pub entry_points: Vec<Address>,
    pub mem: Box<dyn MemoryProvider>,
    pub symbols: SymbolTable,
    pub types: TypeSystem,
    pub functions: FunctionTable,
    pub xrefs: XrefIndex,
    pub patches: PatchSet,
    pub comments: CommentStore,
    pub bookmarks: BookmarkSet,
    pub plugins: PluginContext,
    pub graph: Arc<KnowledgeGraph>,
}
```

`BinaryView` non è `Sync` per default: l'accesso concorrente passa attraverso il `KnowledgeGraph` che è transactional. Le viste UI tengono un `Arc<RwLock<BinaryView>>` ma le mutation passano per il graph event bus.

### 2.7 Architecture trait

```rust
pub trait Architecture: Send + Sync {
    fn name(&self) -> &str;
    fn bits(&self) -> u8;
    fn endian(&self) -> Endian;
    fn calling_conventions(&self) -> &[CallingConvention];
    fn default_cc(&self) -> &CallingConvention;
    fn pointer_size(&self) -> usize;
    fn registers(&self) -> &[RegisterInfo];
    fn max_instr_len(&self) -> usize;
    fn alignment(&self) -> usize;
    
    /// Decode di una singola istruzione a partire dai bytes.
    fn decode(&self, addr: Address, bytes: &[u8]) -> Result<Instruction, DecodeError>;
    
    /// Encode (assembler) di un'istruzione.
    fn encode(&self, instr: &Instruction) -> Result<Vec<u8>, EncodeError>;
    
    /// Lift di un'istruzione a LLIL.
    fn lift(&self, instr: &Instruction, ctx: &mut LiftContext) -> Result<(), LiftError>;
    
    /// Disassembler "text rendering" — non-canonical, per display.
    fn disasm_text(&self, instr: &Instruction, style: DisasmStyle) -> String;
    
    /// Branch targets statici (per CFG building senza eseguire).
    fn branch_targets(&self, instr: &Instruction) -> BranchInfo;
    
    /// Per architetture con stato/contesti (es. x86 16/32/64 bit mode, ARM thumb).
    fn mode_at(&self, addr: Address, view: &BinaryView) -> Mode;
}

#[derive(Clone, Debug)]
pub struct Instruction {
    pub address: Address,
    pub length: u8,
    pub opcode: u32,                  // arch-specific encoding
    pub mnemonic: SmallString<[u8; 16]>,
    pub operands: Vec<Operand>,

}
```

## 3. Loaders — implementazione di ogni formato

### 3.1 PE / PE+

Crate base: `goblin` o `pelite`. La scelta è `goblin` per generalità + `pelite` per analisi PE-specifiche avanzate (rich header, debug directories estesi, .NET metadata).

Step di loading:
1. Parse DOS header, PE header, optional header.
2. Estrai sezioni, build address space virtuale.
3. Detect bitness (PE32 vs PE32+), subsystem, machine.
4. Parse import table (IAT + ILT), export table.
5. Parse relocation directory, applica relocs se base address diverso da preferito.
6. Parse TLS callbacks (importante: malware li usa pre-main).
7. Parse exception directory (.pdata su x64 — fondamentale per function detection senza simboli).
8. Parse load config directory (CFG, GS cookie, SafeSEH).
9. Parse resource directory (manifest, version info, icons — utile per triage).
10. Parse debug directory → trova path PDB associato.
11. Detect .NET: se DataDirectory[14] popolata, è .NET, delega a `rustre-loader-dotnet`.
12. Detect rich header → fingerprint compiler/linker version.
13. Crea entry points (AddressOfEntryPoint + TLS callbacks).

Punti delicati:
- Section .text con file_size < virtual_size (codice unpacked a runtime). Mark come "lazy".
- PE forwarders nelle export (`KERNEL32.HeapAlloc → NTDLL.RtlAllocateHeap`).
- Resource-only DLL (no codice, solo risorse — non causare errori).
- Bound imports (deprecato ma esistente).
- Delay-loaded imports (`__delayLoadHelper2`).

### 3.2 ELF

Crate: `goblin` o `object`. Implementazione standard:
1. Parse ELF header → arch, endian, type (EXEC/DYN/REL).
2. Program headers per layout in memoria (LOAD segments).
3. Section headers per symbol tables, debug info.
4. Dynamic section: NEEDED libraries, RPATH/RUNPATH, dynamic symbols (DT_SYMTAB/DT_STRTAB).
5. Relocation tables: REL/RELA.
6. GNU build-id, debug-link → trovare debug info separato (.debug file via build-id path).
7. Note section: .note.gnu.build-id, .note.ABI-tag.
8. PLT/GOT layout — fondamentale per resolve di indirect calls in stripped binaries.

Architetture comuni in ELF: x86, x86_64, ARM/Thumb, AArch64, MIPS (be/le, o32/n32/n64), RISC-V, PowerPC, SPARC, IBM Z. Handle in `rustre-arch-*`.

### 3.3 Mach-O

Crate: `goblin`. 
- Fat binary detection (universal binaries) → restituisci multipli `BinaryView` come children.
- LC_SEGMENT_64 commands per memory layout.
- LC_SYMTAB, LC_DYSYMTAB per simboli.
- LC_LOAD_DYLIB per dipendenze.
- LC_FUNCTION_STARTS per function detection (Apple lo memorizza esplicitamente — usalo!).
- LC_CODE_SIGNATURE — per analisi codesigning iOS/macOS.
- LC_DYLD_CHAINED_FIXUPS (formato moderno) — replacement di __DATA_CONST.
- dyld_shared_cache — caso speciale: file enorme con tutte le system libs iOS. Parser dedicato (vedere `rustre-mobile-dyld`).

### 3.4 .NET PE

Loader specifico in `rustre-loader-dotnet`. Step:
1. Parse PE base (CLI runtime header in DataDirectory[14]).
2. Parse metadata root → streams (#~, #Strings, #US, #GUID, #Blob).
3. Decode metadata tables (Module, TypeRef, TypeDef, Method, Field, ecc — 50+ tables nello spec ECMA-335).
4. Estrai method bodies (CIL bytecode).
5. Costruisci type hierarchy.
6. Risolvi AssemblyRef → carica dipendenze.

L'output non è un classico `BinaryView` con assembly nativo, ma un `DotnetView` che è un `BinaryView` con `Architecture = CIL`. Le funzioni sono i methods. Disassembler in `rustre-arch-cil`.

### 3.5 Java .class / .jar

Crate: `noak` (Java class file parser pure Rust). Per .jar: ZIP archive (`zip` crate), estrai `*.class`, parse uno alla volta. JAR manifest in `META-INF/MANIFEST.MF`.

Bytecode JVM in `rustre-arch-jvm`. Stack-based, ~200 opcodes, ben documentato in JVMS.

### 3.6 Android APK / DEX

APK = ZIP. Contiene:
- `AndroidManifest.xml` (binary XML — parser dedicato, formato AXML)
- `classes.dex`, `classes2.dex`, ... (Dalvik bytecode)
- `resources.arsc` (binary resource table)
- `lib/<abi>/*.so` (native code — usa loader ELF)
- `assets/`, `res/` (risorse arbitrarie)
- `META-INF/` (firme APK v1/v2/v3/v4)

DEX parser: nessun crate Rust maturo, va scritto. Specifiche Dalvik bytecode pubbliche (https://source.android.com/devices/tech/dalvik/dex-format). 256 opcodes, register-based. Le classi DEX sono il target naturale del decompiler Java/Kotlin.

ART (Android Runtime) compiled output: file `.oat`/`.vdex`/`.art`. Parser separato in `rustre-loader-android`.

### 3.7 WebAssembly

Crate: `wasmparser` (Bytecode Alliance, eccellente).
- Magic: `\0asm\x01\x00\x00\x00`
- Sections: type, import, function, table, memory, global, export, start, element, code, data, custom.
- Bytecode WASM in `rustre-arch-wasm`. Stack-based, tipato.
- Custom sections importanti: `name` (debug symbols), `producers`, DWARF embedded.

### 3.8 Lua bytecode (Lua 5.1, 5.2, 5.3, 5.4)

Formato standard pubblicato. Header:
- Magic `\x1bLua`
- Version (0x51, 0x52, 0x53, 0x54)
- Format version
- Endianness, sizeof(int), sizeof(size_t), sizeof(Instruction), sizeof(lua_Number), integer flag

Function prototype:
- Source name, line defined, last line defined
- num upvalues, num parameters, is_vararg, max stack size
- Code: vector di Instructions (uint32_t opcodes)
- Constants: typed values (NIL, BOOL, NUMBER, STRING)
- Prototypes (nested functions)
- Source lines per instruction
- Local variables debug info
- Upvalue names

Lua VM è register-based (a differenza di JVM/CLR), 38 opcodes in 5.1, ~47 in 5.4. Encoding 32-bit: 6 bit opcode + variazione di operandi (iABC, iABx, iAsBx, iAx).

In `rustre-arch-lua`: decoder, lifter a LLIL, disassembler text. Il decompiler Lua sa che è register-based ma con stack semantic (registers sono in realtà offset dallo stack frame), quindi il lifter LLIL emette `set_reg(R_a, ...)` ma il MLIL le rinomina in `local_<n>` quando rileva la pattern.

Decompiler Lua: relativamente facile vs C decompilation perché Lua mantiene molta info debug (variable names, line numbers). Esistono già `luadec`, `unluac`, `LuaDec51` come reference open source — port to Rust riusando algoritmi noti.

### 3.9 LuaJIT bytecode

Formato diverso da Lua standard. Magic `\x1bLJ`. Bytecode più denso (32-bit ma encoding ottimizzato). ~98 opcodes. Constants in tabelle separate (KGC, KN). 

LuaJIT può anche generare trace-based IR (TIR) tramite tracing JIT — questo è disponibile solo in dump format, non nel bytecode .luac. Quindi per il decompiler, target è solo il bytecode-level.

Reference open source: `luajit-decompiler`, `ljd`. Port to Rust direttamente, eventuali estensioni custom per specifici target via plugin.

### 3.10 Custom / proprietary container formats

Real-world reverse engineering frequently encounters proprietary container formats — encrypted bytecode wrappers, custom asset bundles, vendor-specific signed images. These are by definition not pre-implemented; the platform supports them through the loader plugin trait (sezione 3.1). Typical pipeline implemented by user plugins:

1. **Magic detection**: distinguish container from generic data via fixed header bytes or content heuristics.
2. **Header parsing**: extract version, flags, segment table, signature/checksum offsets.
3. **Key derivation**: derive symmetric keys from in-binary salts, hardware identifiers, or sidecar files (typical scheme: HKDF/Argon2id over context strings).
4. **Decryption / decompression**: usually ChaCha20-Poly1305 / AES-GCM / Salsa20 + optional zstd/lz4.
5. **Integrity check**: BLAKE2b / SHA-256 / signature verification.
6. **Inner format dispatch**: the decrypted payload is typically another format (ELF, PE, LuaJIT bytecode, etc.) — delegate to the corresponding `Loader` implementation.

The plugin SDK (sezione 33) exposes the entire pipeline as Rust traits so an external `Loader` for any proprietary container can plug in without touching the core. Crypto building blocks come from `aes-gcm`, `chacha20poly1305`, `blake2`, `argon2`, `hkdf` crates (RustCrypto suite, all audited).

### 3.11 Firmware

Formati comuni:
- **U-Boot uImage**: header con magic 0x27051956, info su arch/OS/comp, payload (kernel/ramdisk).
- **Intel HEX (.hex)**: ASCII records, line `:CCAAAATTDD...CC`. Parser banale.
- **Motorola S-Record (.srec/.s19)**: simile a HEX.
- **ELF embedded**: ELF normale con `.text` mappato a indirizzi flash. Usa loader ELF.
- **Raw flash dump**: nessun magic. Autodetect: cerca strings noti, calcola entropy per regione, fingerprint compiler-specific patterns. Lascia all'utente la possibilità di forzare arch/endian/base address.
- **DJI/drone firmware, IoT firmware**: spesso archive containers custom. Estrazione con `binwalk`-equivalent in Rust (scrittabile, ~2K righe).

### 3.12 Console formats

- **Nintendo Switch NSO/NRO/NSP/XCI**: NSO è il formato eseguibile, compresso (LZ4 segments), encrypted con keys derivate. Documentati su switchbrew.org. Pubbliche le specifiche.
- **Xbox 360 XEX**: similmente documentato pubblicamente, ha encryption con keys note (Xbox 360 era stato compromesso anni fa).
- **PS3/PS4 ELF / SELF**: ELF con header extra firmati. Tools open: `make_fself`, `scetool`.
- **3DS/Switch homebrew NRO**: simile a NSO ma più semplice.

Ogni console format è un loader plugin separato.

### 3.13 PDF — Crate `rustre-loader-pdf`

PDF è un vettore di malware molto comune (JS embedded, exploit Acrobat, launch actions). Loader strutturale:

- **Parser**: `lopdf` crate per parsing oggetti, xref, trailer, stream. Supporta encrypted PDFs (RC4/AES). Per PDFs malformati (deliberatamente offuscati per evadere parsers), fallback parser tollerante che ricostruisce xref via scan lineare.
- **Object extraction**: enumera tutti gli `Indirect Object`. Per ogni oggetto identifica tipo (Stream, Dictionary, Array, Name, String, Number).
- **Suspicious pattern detection**:
  - `/JavaScript`, `/JS` → estrai JS code, analizza separatamente (heuristics + AST-based via `boa` o `swc` JavaScript engines in Rust)
  - `/OpenAction`, `/AA` (Additional Actions) → auto-trigger su apertura
  - `/Launch` → esecuzione esterna
  - `/EmbeddedFile` → file embedded (tipico drop di payload)
  - `/URI` → external link
  - `/RichMedia`, `/Flash` → SWF embedded (legacy ma ancora visti)
  - `/XFA` → XML Forms Architecture (exploit vector)
  - `/Names` con entry sospetti
- **Stream decoder**: gestisce filters multipli (FlateDecode, ASCIIHexDecode, ASCII85Decode, LZWDecode, RunLengthDecode, CCITTFaxDecode, JBIG2Decode, DCTDecode, JPXDecode, Crypt). FlateDecode con predictor PNG.
- **JS extraction & analysis**: JavaScript stream → tokenizer → AST → individua pattern noti (heap spray, ROP gadget construction, shellcode escape sequences `unescape("%uXXXX")`)
- **Exploit detection**: signatures su CVE noti (CVE-2010-2883 PDF /Encrypt, CVE-2013-3346 ToolButton, CVE-2018-4990 ecc.)
- **BinaryView output**: il PDF è esposto come un BinaryView gerarchico (root, objects, streams) — ogni stream è un sub-view analizzabile con disassembler text/binary appropriate.

Tools di riferimento (open source, da port-are/superare): peepdf, pdf-parser (Didier Stevens), pdfid.py.

### 3.14 Office OLE / OOXML / VBA — Crate `rustre-loader-ole`

Documenti Office sono un altro vettore comune (macro VBA, exploit Equation Editor, DDE, template injection, OLE objects). Tre sotto-formati:

**OLE Compound Document (vecchi .doc/.xls/.ppt + container moderno per `vbaProject.bin`)**:
- Filesystem-like binary container (Microsoft Compound File Binary Format / CFBF, documentato in MS-CFB)
- Parser: scrivere `rustre-cfb` (~1500 righe Rust) — leggi MSAT, SAT, SSAT, directory streams, mini-stream. Esistono `cfb` crate Rust ma minimale, lo estendiamo.
- Enumera tutti gli stream e storages, mappali in BinaryView gerarchico.

**OOXML (.docx/.xlsx/.pptx + macro varianti .docm/.xlsm/.pptm)**:
- ZIP archive con XML interno (parts via `[Content_Types].xml` + `_rels/.rels`)
- Parser: `zip` crate + `quick-xml` per parsing relazioni e content
- Cerca `word/vbaProject.bin`, `xl/vbaProject.bin`, `ppt/vbaProject.bin` per macro
- Cerca `word/_rels/document.xml.rels` per external template injection (remote template loading)
- Cerca `word/embeddings/*.bin` per OLE objects embedded

**VBA Project Parsing** (MS-OVBA documentato pubblicamente):
- Parse `dir` stream: project info, references, module list
- Per ogni module: parse stream (compressed VBA p-code + decompressed source text if not stripped)
- VBA compression: custom RLE-like, algoritmo documentato in MS-OVBA section 2.4.1
- VBA P-code decompiler: i pattern di opcodes sono noti (vbadump tool come reference). VBA stub mostra source nella forma stripped, ma p-code nello stream è il "vero" codice eseguito — se differiscono è "VBA Stomping" (defense evasion). Detect + report mismatch.
- Output: BinaryView con stream VBA come "source code views" + p-code disassembly view
- Macro analysis: ulteriormente espone macro a YARA (sezione 22), pattern matching su API sospette (`Shell`, `CreateObject("WScript.Shell")`, `URLDownloadToFile`, `Environ`, autoexec triggers `Document_Open`/`AutoOpen`/`Workbook_Open`)

**Detection extra**:
- DDE attacks: `DDEAUTO` field codes in document XML
- Template injection: external template URL in `settings.xml.rels`
- Equation Editor (CVE-2017-11882, CVE-2018-0802): detect embedded OLE object with CLSID `{0002CE02-...}`
- RTF specific: parser RTF separato (formato testuale), cerca `\objdata` con embedded OLE, `\object\objemb` patterns

Tools di riferimento: olevba (Decalage), oletools suite, MalDoc, vbadump.

### 4.1 x86 / x86_64

Crate: `iced-x86`. È il disassembler x86 più veloce e accurato esistente. Supporta:
- 16/32/64-bit modes
- AVX, AVX2, AVX-512 (tutte le estensioni)
- AMX, APX
- Decoder + encoder (assembler)
- Tutti i prefissi, segment overrides
- Operandi tipizzati

Implementazione `rustre-arch-x86::X86Arch`:

```rust
pub struct X86Arch { 
    bits: u8,
    decoder_options: u32, // iced-x86 DecoderOptions
}

impl Architecture for X86Arch {
    fn decode(&self, addr: Address, bytes: &[u8]) -> Result<Instruction, DecodeError> {
        use iced_x86::{Decoder, DecoderOptions};
        let mut decoder = Decoder::with_ip(
            self.bits as u32,
            bytes,
            addr.0,
            self.decoder_options,
        );
        let iced_instr = decoder.decode();
        if iced_instr.is_invalid() {
            return Err(DecodeError::Invalid);
        }
        Ok(self.convert_to_rustre_instr(iced_instr))
    }
    // ... encode via iced_x86::Encoder
    // ... lift in 4.1.1
    // ... branch_targets analizzando iced_instr.flow_control()
}
```

#### 4.1.1 Lift x86 → LLIL

Questa è la parte non triviale. Devi tradurre ogni opcode in operazioni LLIL primitive. Per ~3000 opcodes x86 (con tutte le varianti) non si scrive a mano — si usa una tabella di handlers per categoria. Categorie principali:

- **Data movement**: MOV, MOVZX, MOVSX, MOVSXD, LEA, XCHG, CMPXCHG, MOVNTI, MOVDQA, ecc.
- **Arithmetic**: ADD, SUB, ADC, SBB, MUL, IMUL, DIV, IDIV, INC, DEC, NEG, AAA/AAS (legacy).
- **Logical**: AND, OR, XOR, NOT, TEST, BTS, BTR, BTC.
- **Shifts**: SHL/SAL, SHR, SAR, ROL, ROR, RCL, RCR, SHLD, SHRD.
- **Control flow**: JMP (rel/indirect), Jcc (16 condition codes), CALL, RET, RETN, IRET, JECXZ.
- **String ops**: MOVS, CMPS, SCAS, LODS, STOS, INS, OUTS (+ REP/REPNE prefixes).
- **Stack**: PUSH, POP, PUSHA/POPA (16/32 only), ENTER, LEAVE, PUSHF, POPF.
- **Flag ops**: CLC, STC, CMC, CLD, STD, CLI, STI, LAHF, SAHF.
- **Conditional moves**: CMOVcc (16 varianti).
- **Set on condition**: SETcc (16 varianti).
- **System**: SYSCALL, SYSENTER, SYSEXIT, INT, INT3, INT1, UD2, CPUID, RDTSC, RDMSR, WRMSR.
- **FPU x87**: FADD, FSUB, FMUL, FDIV, FLD, FST, FSTP, FCOM, ecc.
- **MMX/SSE/AVX**: PADDB, PSUBW, PMULLW, MOVAPS, ADDPS, XORPS, VADDPS, ecc.
- **AVX-512**: con masking (k registers) e EVEX encoding.

Per ognuno: handler funzione che prende `(instr, ctx) → ()` e emette LLIL ops. Esempio:

```rust
fn lift_add(instr: &iced_x86::Instruction, ctx: &mut LiftContext) -> Result<(), LiftError> {
    let dst = operand_to_llil(&instr.op0(), ctx)?;
    let src = operand_to_llil(&instr.op1(), ctx)?;
    let size = instr.op0_register().size().max(instr.memory_size().size());
    
    // result = dst + src
    let result = ctx.emit(LlilOp::Add { 
        size, 
        lhs: dst.clone(), 
        rhs: src 
    });
    
    // Update flags: CF, OF, SF, ZF, AF, PF
    ctx.emit_flag_set(Flag::Cf, LlilOp::CarryFromAdd(result.clone()));
    ctx.emit_flag_set(Flag::Of, LlilOp::OverflowFromAdd(result.clone()));
    ctx.emit_flag_set(Flag::Sf, LlilOp::Sign(result.clone()));
    ctx.emit_flag_set(Flag::Zf, LlilOp::IsZero(result.clone()));
    ctx.emit_flag_set(Flag::Af, LlilOp::Aux(result.clone()));
    ctx.emit_flag_set(Flag::Pf, LlilOp::Parity(result.clone()));
    
    // Store result in dst
    ctx.emit(LlilOp::Store { dst, value: result });
    
    Ok(())
}
```

Volume di codice stimato per lifter x86/x64 completo: ~30-50K righe. Parallelizzabile con AI (chiedi all'agente di scrivere ogni handler con i test) ma serve un essere umano che verifichi su un test corpus di binari reali e benchmark vs Ghidra/BN.

### 4.2 ARM/ARM64

Crate primario: `bad64` per AArch64 (decoder pure Rust ottimo, copertura ISA recente). Fallback `capstone-rs` per ARM 32 (Thumb1/Thumb2 + ARM mode).

AArch64 specifics:
- Fixed 32-bit instruction encoding (4 bytes ogni istruzione).
- 31 GP registers (X0-X30) + SP + PC + flag register.
- Mode switching Thumb non esiste in A64.
- SVE/SVE2 vector extension (variable-length vectors).
- Pointer authentication (PAC) — usato pesantemente su iOS/macOS recente.

ARM 32 specifics:
- 32-bit ARM mode + 16/32-bit Thumb mode + ThumbEE (deprecated) + Jazelle (deprecated).
- 16 GP registers (R0-R15, R15=PC).
- Condition codes prefix su ogni istruzione ARM (non Thumb).
- Modes (USR, FIQ, IRQ, SVC, ABT, UND, SYS) con register banking.

Mode detection è critico: in stripped ARM binary, bit 0 del puntatore funzione indica Thumb (lo trovi in symbol value LSB). Il `mode_at()` del trait Architecture risolve.

### 4.3 MIPS / RISC-V / PowerPC / SPARC

Tutti via `capstone-rs`. Decoder solo, no lift. Per lifting: o porta Ghidra Sleigh files per queste architetture (esistono in p-code) o scrivi handlers a mano (sono ISA più piccole, ~200-400 opcodes).

RISC-V vector extension (RVV) è in evoluzione rapida, capstone potrebbe non avere copertura completa — fallback al binutils objdump in subprocess come sanity check.

### 4.4 Retro architetture (6502, Z80, 68k)

Crate dedicati `rustre-arch-6502`, `rustre-arch-z80`, `rustre-arch-68k`. Decoder via capstone (supporta tutte e tre). Utile per RE di sistemi embedded retro, vintage hardware, ROM analysis di sistemi industriali legacy still-in-use, emulator development. Volume basso di opcode, lifter scrittabile a mano in poche K righe per arch. Particolarmente: 6502 (~56 opcodes), Z80 (~158 opcodes + prefisi), 68k (CISC con encoding complesso, ~80 instruction classes con molti modi di addressing).

### 4.5 MCU (AVR, MSP430, PIC)

Crate `rustre-arch-avr`, `rustre-arch-msp430`. AVR e MSP430 via capstone. PIC: niente in capstone, ma ~35-80 opcodes a seconda della famiglia (PIC12/16/18/24/32) — scrivibile a mano in `~2K righe` per famiglia. Importante per IoT firmware, automotive ECUs, industrial controllers.

### 4.6 eBPF / cBPF — Crate `rustre-arch-bpf`

eBPF (extended Berkeley Packet Filter) è oggi runtime fondamentale del kernel Linux: hooks per network filtering (XDP, TC), tracing (kprobes, tracepoints, uprobes), security (LSM hooks), syscalls filtering (seccomp). Recentemente è anche vettore di rootkit (BPFDoor, Symbiote, BPFedoor): malware modern Linux usa BPF perché esegue in kernel context con bypass di EDR userspace.

Coperture:
- **cBPF (classic)**: 64-bit instructions, 2 registers (A, X), legacy. ~30 opcodes. Usato ancora in `tcpdump`, `seccomp-bpf`.
- **eBPF**: 64-bit instructions a 8 byte fissi, 11 registers (r0-r10), 32/64-bit ops, JIT-able, helper functions. Opcode encoding documentato in `Documentation/networking/filter.txt` del kernel + IETF draft "BPF Instruction Set Architecture".

Implementazione:
```rust
pub struct BpfArch {
    variant: BpfVariant,  // Classic, Extended
}

pub enum BpfInstruction {
    Alu { op: AluOp, dst: BpfReg, src: BpfSrc, size: BpfSize },
    Jmp { op: JmpOp, dst: BpfReg, src: BpfSrc, offset: i16 },
    Load { dst: BpfReg, src: BpfReg, offset: i16, size: BpfSize },
    Store { src: BpfReg, dst: BpfReg, offset: i16, size: BpfSize },
    AtomicOp { op: AtomicOp, dst: BpfReg, src: BpfReg, offset: i16, size: BpfSize },
    Call(BpfHelperOrId),
    Exit,
    LoadImm64 { dst: BpfReg, value: u64 },
}
```

eBPF semantics richiede:
- **Helper function database**: ~200 helpers definiti in `uapi/linux/bpf.h`, ognuno con prototype noto (es. `bpf_map_lookup_elem(map, key) -> value_ptr`, `bpf_probe_read(dst, size, src)`, `bpf_get_current_pid_tgid() -> u64`). Database autogenerabile da `bpf.h` headers parsed.
- **Map operations recognition**: i programmi BPF interagiscono con `BPF_MAP_TYPE_*` (HASH, ARRAY, RINGBUF, PERF_EVENT_ARRAY ecc.). L'analisi traccia map descriptors e visualizza schema.
- **Section semantics**: nel formato BPF object (ELF), sections come `xdp/`, `tc/`, `kprobe/`, `tracepoint/sched/sched_switch`, `lsm/`, `socket/` indicano il context di attachment. Loader BPF capisce sections, le associa al type di program.
- **CO-RE relocations**: Compile-Once-Run-Everywhere usa BTF (BPF Type Format) per relocate field accesses across kernel versions. Parser BTF (in formato ELF section `.BTF` / `.BTF.ext`) — esistono crate `btf` e `aya` Rust come reference.
- **Verifier modeling**: il kernel BPF verifier impone restrizioni (no unbounded loops, register state tracking, bounded stack 512B, pointer arithmetic constrained). Per analisi, modelliamo il verifier in symbolic execution per identificare "may not load" patterns.

Use cases del crate:
1. Reversare programmi BPF malicious (BPFDoor & similar rootkit)
2. Analizzare programmi BPF di sicurezza (Falco, Tetragon) per audit
3. Custom seccomp filter inspection
4. tcpdump filter analysis (cBPF compiled da pcap filter expression)
5. Network XDP/TC pipeline reverse engineering

### 4.7 Bytecode VMs (CIL, JVM, DEX, Lua, LuaJIT, WASM)

Già coperti nei loader. Ognuno ha il suo arch crate dedicato (`rustre-arch-cil`, `rustre-arch-jvm`, `rustre-arch-dex`, `rustre-arch-lua`, `rustre-arch-luajit`, `rustre-arch-wasm`) con decoder, semantica VM-specifica per il lifter LLIL, e mapping a strutture concettuali (stack slot vs register vs local) appropriato per ogni VM.

### 4.8 Custom / unknown architecture

Se un utente carica un binario di un'architettura non supportata (custom SoC, vintage CPU, DSPs), Sleigh format support: porta `sleigh-rs` (immature) o tieni Sleigh runtime via FFI a `libsla` di Ghidra. Sleigh ha già spec files per molte CPU obscure (Z180, Tricore, V850, TI C6000, Tilera Tile, M68HC, PowerISA varianti). User può anche definire una nuova arch via scripting (sezione 33): Rhai/Lua/Python script che implementa il trait `Architecture` runtime.

## 5. IR multi-livello

### 5.1 LLIL (Low Level IL)

Pensata come una "macchina di Turing tipizzata". Ogni istruzione asm produce 1-N LLIL ops.

```rust
#[derive(Clone, Debug)]
pub enum LlilOp {
    // Memory
    Load { size: Size, addr: LlilExpr },
    Store { size: Size, addr: LlilExpr, value: LlilExpr },
    
    // Register / variable
    GetReg { reg: RegId, size: Size },
    SetReg { reg: RegId, value: LlilExpr },
    GetFlag { flag: FlagId },
    SetFlag { flag: FlagId, value: LlilExpr },
    
    // Constants
    Const { value: i128, size: Size },
    ConstPtr { value: u64 },
    
    // Arithmetic
    Add(Box<LlilExpr>, Box<LlilExpr>),
    Sub(Box<LlilExpr>, Box<LlilExpr>),
    Mul(Box<LlilExpr>, Box<LlilExpr>),
    DivU(Box<LlilExpr>, Box<LlilExpr>),
    DivS(Box<LlilExpr>, Box<LlilExpr>),
    ModU(Box<LlilExpr>, Box<LlilExpr>),
    ModS(Box<LlilExpr>, Box<LlilExpr>),
    
    // Logical / bitwise
    And(Box<LlilExpr>, Box<LlilExpr>),
    Or(Box<LlilExpr>, Box<LlilExpr>),
    Xor(Box<LlilExpr>, Box<LlilExpr>),
    Not(Box<LlilExpr>),
    
    // Shifts / rotates
    Lsl(Box<LlilExpr>, Box<LlilExpr>),
    Lsr(Box<LlilExpr>, Box<LlilExpr>),
    Asr(Box<LlilExpr>, Box<LlilExpr>),
    Rol(Box<LlilExpr>, Box<LlilExpr>),
    Ror(Box<LlilExpr>, Box<LlilExpr>),
    
    // Comparison
    CmpEq(Box<LlilExpr>, Box<LlilExpr>),
    CmpNe(Box<LlilExpr>, Box<LlilExpr>),
    CmpLtU(Box<LlilExpr>, Box<LlilExpr>),
    CmpLtS(Box<LlilExpr>, Box<LlilExpr>),
    CmpLeU(Box<LlilExpr>, Box<LlilExpr>),
    CmpLeS(Box<LlilExpr>, Box<LlilExpr>),
    // ... gt/ge
    
    // Size manipulation
    SignExtend { value: Box<LlilExpr>, to_size: Size },
    ZeroExtend { value: Box<LlilExpr>, to_size: Size },
    Truncate { value: Box<LlilExpr>, to_size: Size },
    
    // Control flow
    Jump { target: LlilExpr },
    JumpIf { cond: LlilExpr, true_target: u64, false_target: u64 },
    Call { target: LlilExpr },
    Tailcall { target: LlilExpr },
    Return { value: Option<LlilExpr> },
    
    // Floating point (similar ops with F prefix)
    FAdd(...), FSub(...), FMul(...), FDiv(...),
    FCmpEq(...), FCmpLt(...),
    IntToFloat(...), FloatToInt(...),
    
    // SIMD / vector
    VAdd { lanes: u8, lane_size: Size, lhs: Box<LlilExpr>, rhs: Box<LlilExpr> },
    // ... molti altri
    
    // System / intrinsic
    Syscall { num: LlilExpr, args: Vec<LlilExpr> },
    Intrinsic { name: String, args: Vec<LlilExpr> },
    Unimplemented,
    NoReturn,
}
```

Ogni `LlilExpr` ha una size. Type-checking è semplice ma rigoroso.

### 5.2 MLIL (Medium Level IL) — SSA form

Trasformazione LLIL → MLIL:
1. Build basic blocks dal flow control.
2. Convert in SSA: ogni assegnamento a register/temp riceve un index (`rax_1`, `rax_2`, ...), insert PHI nodes nei join points.
3. Calling convention awareness: arg registers (e.g. RDI, RSI, RDX su SysV x86-64 Linux) diventano `arg0`, `arg1` per le funzioni.
4. Stack frame analysis: identifica RSP/RBP usage, sostituisce `[rbp-0x10]` con `local_10`.
5. Constant propagation, dead code elimination, common subexpression elimination.
6. Flag rebuilding: dove possibile, sostituisci `cmp+jcc` con `if (a < b)`.

Output: ogni MLIL statement è ancora atomico ma con variabili nominate (non più registri raw), assignments single-static.

```rust
#[derive(Clone, Debug)]
pub enum MlilStmt {
    Assign { dst: Variable, value: MlilExpr, version: u32 },
    Phi { dst: Variable, sources: Vec<(BBId, Variable)> },
    Call { ret: Option<Variable>, target: MlilExpr, args: Vec<MlilExpr> },
    Return(Option<MlilExpr>),
    Branch { cond: MlilExpr, true_bb: BBId, false_bb: BBId },
    Jump(BBId),
    Store { dst: MlilExpr, value: MlilExpr },
    // ...
}
```

Per la conversione SSA, algoritmo classico: dominance frontier + iterated PHI placement (Cytron et al 1991). Crate Rust utili: `petgraph` per il dominator tree, scrivere te il rest.

### 5.3 HLIL (High Level IL)

MLIL → HLIL = control flow structuring + type recovery + expression nesting.

#### 5.3.1 Control flow structuring

L'algoritmo migliore documentato è quello del paper DREAM "No More Gotos" (Yakdan et al. NDSS 2015). Approccio:

1. Identifica regioni single-entry single-exit nel CFG.
2. Pattern-independent: invece di matchare schema rigidi (Cifuentes), usa **interval analysis + reachability** per dedurre struttura.
3. Loop refinement: identifica head/tail, determina while/do-while/for.
4. Condition recovery: combina basic block conditions in espressioni boolean composite, evitando goto.
5. Switch detection: cluster di jump table o cmp/je chains → switch statement.

Implementazione concreta in `rustre-decompiler-cfs`:
- DAG di "structuring regions"
- Algoritmo bottom-up: collapsa region in nodo singolo, ripeti
- Quando non si può più collapsare e c'è cycle, usa Tarjan SCC per identificare loop natural/improper
- Improper loops → goto (inevitabile in alcuni casi)
- Fallback: "comb" algorithm (Basque-Vidal et al. AsiaCCS 2020) per goto reduction in casi pathological

#### 5.3.2 Expression nesting

In MLIL: `t1 = a + b; t2 = t1 * c; r = t2;` 
In HLIL: `r = (a + b) * c;`

Algoritmo: per ogni assegnamento a variabile temporanea usata once-only, sostituisci uso con l'espressione. Attenzione a side effects (memory loads, calls).

#### 5.3.3 Type recovery

Sopra in sezione 7.


## 6. Analysis framework

### 6.1 Function detection

Più strategie combinate per massima copertura:

**Strategy 1: Exception directory (Windows PE x64)**. `.pdata` contiene `RUNTIME_FUNCTION { BeginAddress, EndAddress, UnwindData }` per ogni funzione non-leaf. Su Windows x64 ufficiale, **tutte** le funzioni che usano stack frame devono averlo. Copre il 95% di binari MSVC.

**Strategy 2: Mach-O LC_FUNCTION_STARTS**. Apple memorizza esplicitamente l'inizio di ogni funzione. Usalo direttamente.

**Strategy 3: ARM EHABI `.ARM.exidx`**. Equivalente di `.pdata` per ARM.

**Strategy 4: DWARF `.eh_frame` / `.debug_frame`**. Stack unwinding info da `gcc`/`clang`. Indica function boundaries.

**Strategy 5: Symbols**. Se PDB/DWARF/symtab fornisce nomi, ogni nome con kind FUNC è una funzione.

**Strategy 6: Call targets**. Ogni indirizzo target di una `call` istruzione è candidate funzione.

**Strategy 7: Prologue signatures**. Pattern come `push rbp; mov rbp, rsp` (x86), `stp x29, x30, [sp, ...]` (ARM64), `sub rsp, N` (no-frame x64). Database di pattern per ogni arch.

**Strategy 8: Linear sweep**. Disassembla sequenzialmente da inizio sezione codice, considera ogni inst dopo `ret`/`jmp`/`ud2` come potenziale start.

**Strategy 9: Recursive descent**. Da entry point, segui flow, ogni call → nuova funzione.

Combina tutte le strategie con un confidence score, risolvi conflitti. Algoritmo merge: lattice di confidence, vince la strategy più alta che non è invalidata da una più alta.

### 6.2 CFG construction

Per ogni funzione: parti da `start`, disassembla istruzioni, ogni branch crea edges. Basic block boundaries:
- Inizio block: target di un branch, fallthrough da branch precedente, prima istruzione funzione.
- Fine block: branch (cond/uncond), call (se chiama no-return function), ret, ud2, syscall a no-return (exit, abort).

Strutture:

```rust
pub struct BasicBlock {
    pub id: BBId,
    pub start: Address,
    pub end: Address,            // ultima istruzione inclusa
    pub instructions: Vec<InstrId>,
    pub successors: Vec<(BBId, EdgeKind)>,
    pub predecessors: Vec<BBId>,
}

#[derive(Copy, Clone, Debug)]
pub enum EdgeKind {
    Fallthrough,
    Jump,
    BranchTaken,
    BranchNotTaken,
    Call,
    Return,
    Exception,
    Unresolved,  // indirect jump non risolto
}
```

Caso speciale: jump table (switch statement). Detection:
- Pattern `jmp [reg*8 + table_base]` (x86)
- Validazione: gli entries della table devono essere indirizzi validi nella stessa funzione
- Risolto via VSA (value-set analysis) per i bounds

### 6.3 Cross-references (xrefs)

Tre tipi principali:
- **Code → code**: call/jump da indirizzo A a indirizzo B.
- **Code → data**: lea/load/store referenzia data segment.
- **Data → code/data**: data segment contiene pointer (vtables, function pointers, jump tables).

Algoritmo: per ogni istruzione, esamina operandi:
- Immediate value che cade in mem regions → potential xref
- Memory reference con base+disp dove base è noto / risolvibile → xref
- Indirect via register: VSA per risolvere quando possibile

Storage: tabella `xrefs` come da schema sopra. Index su `to_addr` per query "chi referenzia X".

### 6.4 String detection

Algoritmo:
1. Scanning lineare delle sezioni data (`.rdata`, `.data`, `.rodata`) per sequenze di bytes che sembrano stringhe:
   - ASCII printable: 4+ chars + null terminator
   - UTF-16LE: 4+ chars con high byte 0
   - UTF-8: heuristic detection (uchardet-style)
2. Per ogni string trovato: cerca xref da code → emergono "string usage points"
3. Decoding: detect encoding, store come `(address, length, encoding, decoded)`.

Edge cases: obfuscated strings (XOR'd, encrypted), stack strings (mov [rsp+X], byte/word at runtime), DLL resource strings (parse `.rsrc`).

Per stack strings: pattern detection in MLIL (sequenze di store consecutive a stack offsets adiacenti con valori costanti) + simulazione di esecuzione per accumulare la string.

### 6.5 Calling convention detection

Per funzione senza simboli, identifica CC heuristicamente:
- Quali argomenti registers letti prima di essere scritti? (usage)
- Stack cleanup chi lo fa? (caller vs callee — diff cdecl vs stdcall)
- Return register usata? (RAX/EAX, XMM0 per float)
- Preservation registers (RBX, RBP, R12-R15 in SysV x64)

Database di CC noti per arch+OS+compiler. Match il pattern observed. Confidence score.

### 6.6 Type recovery

Approccio multilivello:

**Level 1 — Sized variables**. Da accessi memoria deduci size (byte, word, dword, qword).

**Level 2 — Primitive types**. Distingui int/uint da operazioni (signed shift = signed type, division signed/unsigned). Float/double da uso di SSE/AVX float instructions.

**Level 3 — Pointer types**. Variabili dereferenziate come `[var + offset]` → pointer.

**Level 4 — Struct inference**. Multipli access pattern `*(ptr + 0)`, `*(ptr + 4)`, `*(ptr + 8)` → struct con fields a quegli offset.

**Level 5 — Array inference**. Accesso pattern `*(ptr + i*4)` dove i è loop variable → array di tipo da 4 bytes.

**Level 6 — Class/vtable inference**. Pointer caricato da `[obj_ptr]` poi chiamato via call indirect → vtable. Cluster vtables, identifica RTTI structure (MSVC), `__cxa_*` (Itanium ABI).

**Level 7 — Library function signatures**. Se FLIRT/sigs matchano una funzione a libc o WinAPI nota, importa i tipi degli argomenti (e propaga ai callers).

Implementazione: framework di constraint solving. Ogni "type fact" è un constraint, sistema risolto incrementalmente con union-find + lattice di types.

### 6.7 Library function recognition (FLIRT-style)

Vedere sezione dedicata (17).

### 6.8 Indirect call/jump resolution

Pattern:
```
mov rax, [vtable_ptr]
call rax
```
o
```
call [import_table_entry]
```

Strategie:
- Symbol-based: import table → target è external function noto.
- VSA: traccia il value-set di `rax` a quel punto.
- Type-based: se vtable_ptr ha type `MyClass*` e `MyClass` ha vtable noto, l'entry è la funzione virtuale a quell'offset.
- Runtime trace: se hai un trace TTD, leggi l'indirizzo effettivo.

## 7. Symbols (PDB, DWARF, CodeView, STABS, embedded)

### 7.1 PDB (Microsoft)

Crate: `pdb` (https://github.com/willglynn/pdb). Pure Rust, completo.

Step:
1. Open PDB file (companion del PE, path da Debug Directory).
2. Estrai global symbols (`GlobalSymbols` stream).
3. Estrai module symbols (per ogni module/compiland).
4. Public symbols (function names esposti).
5. Section contributions (mappa addr → module).
6. Type information (`TPI` stream) — struct, class, enum, typedef.
7. Build info: paths, compiler version.

Mapping a `BinaryView`:
- Per ogni `Symbol::Procedure`: registra come funzione con name demangled.
- Per `Symbol::Data`: registra come data symbol.
- Per `Symbol::UserDefinedType`: registra in TypeSystem.

PDB v7 (standard moderno) ben supportato dal crate. PDB v2 (MSVC <6.0) parser separato se serve.

### 7.2 DWARF

Crate: `gimli` (Bytecode Alliance, eccellente). + `addr2line` come layer di convenience.

DWARF è MOLTO complesso. Versioni 2, 3, 4, 5 in giro. DWARF 5 ha cambiamenti significativi (split DWARF, location lists v5, ecc.).

Step base:
1. Trova sezioni: `.debug_info`, `.debug_abbrev`, `.debug_line`, `.debug_str`, `.debug_loc`/`.debug_loclists`, `.debug_ranges`/`.debug_rnglists`, `.debug_aranges`, `.debug_pubnames`, `.debug_frame`/`.eh_frame`.
2. Parse CU (Compilation Units), DIEs (Debug Information Entries).
3. Estrai function info: DW_TAG_subprogram con DW_AT_low_pc/DW_AT_high_pc.
4. Variables: DW_TAG_variable, DW_TAG_formal_parameter con DW_AT_location.
5. Types: DW_TAG_base_type, DW_TAG_structure_type, DW_TAG_pointer_type, DW_TAG_array_type.
6. Line numbers: line program in `.debug_line`.
7. Split DWARF: `.dwo` files per dimensioni ridotte.

DWARF location expressions sono una mini-VM (opcodes DW_OP_*). Implementa interpreter completo. Locations possono cambiare per range di PC (loclist) — implementa anche quello.

### 7.3 CodeView (legacy MS)

Vecchi PE possono avere CodeView embedded (`.debug$S` sezione). Implementazione: parser dedicato (specifiche pubbliche su MSDN). Volume basso oggi.

### 7.4 STABS (legacy Unix)

Vecchi binari ELF/COFF con `.stab`/`.stabstr`. Documentato in "stabs.pdf" GDB docs. Implementazione: parser dedicato, volume basso.

## 8. Decompiler completo

Questo è uno dei componenti più complessi. Va costruito incrementalmente.

### 8.1 Pipeline

```
asm bytes
  → decode (Architecture::decode)
  → CFG building
  → LLIL lifting (Architecture::lift)
  → IR passes (const prop, DCE, CSE, VSA, ...)
  → MLIL lowering (SSA form, calling conv resolved)
  → Type recovery
  → HLIL lowering (control flow structuring, expression nesting)
  → C-like emission
```

### 8.2 SSA construction

Algoritmo standard Cytron-Ferrante-Rosen-Wegman-Zadeck (POPL 1991):
1. Compute dominator tree del CFG (algoritmo Lengauer-Tarjan).
2. Compute dominance frontier.
3. Place PHI nodes: per ogni variable defined in BB X, insert PHI in tutte BB in DF(X).
4. Rename: walk dominator tree, mantieni stack di "current version" per ogni variable, sostituisci usi col version corretto, push/pop entrando/uscendo da BB.

Crate: `petgraph::algo::dominators::simple_fast` per dominator tree. Resto da scrivere.

### 8.3 Calling convention resolution

Per ogni funzione:
1. Identifica argument registers usati (live-in al primo BB).
2. Identifica return register (last write before ret in exit BB).
3. Match contro CC database per arch+ABI (SysV x86-64, Microsoft x64, AAPCS, ecc.).
4. Promuovi `arg0`, `arg1`, ... a parametri della funzione.
5. Identifica callee-saved registers preservation pattern → rimuovi dal output.

### 8.4 Stack frame analysis

Pattern detection per RBP-based vs RSP-based frames:
- RBP-based: `push rbp; mov rbp, rsp; sub rsp, N` → locals a `[rbp-X]`, params a `[rbp+16]+`
- RSP-based (frame pointer omission): `sub rsp, N`, locals a `[rsp+X]`

Algoritmo:
1. Identifica frame setup nel prologue.
2. Identifica frame teardown nell'epilogue.
3. Tutti `[rbp/rsp ± const]` → variabili locali nominate `local_X`, `arg_X`.
4. Stack depth tracking: VSA su RSP per sapere a ogni punto dove sta.

### 8.5 Control flow structuring (DREAM/Comb algorithm)

Implementazione di "No More Gotos" (Yakdan 2015) + miglioramenti "Comb" (2020).

Fase 1: Loop detection.
- Identifica SCCs nel CFG (Tarjan's algorithm).
- Per ogni SCC non triviale: è un loop.
- Determina loop header (entry node), loop body, exit nodes.
- Classifica: natural loop (single entry) vs improper (multiple entries — richiede node splitting o goto).

Fase 2: Condition aware structuring.
- Per ogni nodo non in loop: cerca pattern if-then, if-then-else.
- Build "condition aware graph": ogni edge ha una condition (a sequence of taken/not-taken da basic blocks branchanti).
- Identify single-entry single-successor regions.

Fase 3: Switch recovery.
- Pattern: indirect jump da jump table → switch.
- Pattern: cmp/je chain con incrementing values → switch.

Fase 4: Goto elimination (Comb approach).
- Quando impossibile structurare cleanly, posiziona goto in modo che il codice sia leggibile (minimize goto count, prefer forward gotos over backward).

Output: AST HLIL strutturato.

### 8.6 Expression reconstruction

Da MLIL SSA con tante temporary variables, ricostruisci espressioni nestate:

```rust
fn fold_expressions(stmts: &mut Vec<MlilStmt>) {
    let mut def_use_count = compute_def_use_count(stmts);
    
    // Per ogni temp variabile usata solo 1 volta, sostituisci uso con definizione
    for i in 0..stmts.len() {
        if let MlilStmt::Assign { dst, value, .. } = &stmts[i] {
            if def_use_count[dst] == 1 && !has_side_effect(value) {
                let use_site = find_use(stmts, dst, i + 1);
                if let Some((j, replace_fn)) = use_site {
                    replace_fn(stmts, value.clone());
                    stmts.remove(i);
                }
            }
        }
    }
}
```

Cautele:
- Mai inline expressions con side effects (memory loads — se memoria può cambiare, calls).
- Mai inline attraverso loop boundaries.
- Mai inline se l'ordine di valutazione conta (volatile, atomic).

### 8.7 Type-aware decompilation

Una volta che hai type recovery, applica nel rendering:
- `*(int*)(ptr + 0x10)` → `ptr->field_10` se ptr ha struct type
- `*(char**)(arr + i * 8)` → `arr[i]` se arr è `char**`
- `(SomeClass*)ptr` → cast explicit dove tipo cambia

### 8.8 C-like emission

Pretty printer. Configura:
- Indent style (spaces/tabs)
- Brace style (Allman, K&R)
- Cast verbosity
- Constant rendering (hex vs dec, with size suffix)
- Variable naming convention

Output deve essere ri-compilabile in molti casi (importante per testing decompiler quality — compila l'output, decompila di nuovo, dovrebbe stabilizzarsi).

### 8.9 Decompiler quality metrics

Per misurare se il tuo decompiler è buono:
- **Recompilability**: % di funzioni output che compila con `gcc -c`.
- **Semantic equivalence**: % di funzioni dove la versione originale e ricompilata hanno stesso behavior (test suite).
- **Goto count per function**: meno è meglio.
- **Variable naming**: dummy `var_4` vs nomi recovered.
- **Expression density**: linee di codice (meno = più espressivo).

Benchmark contro Ghidra, IDA Hex-Rays, BinaryNinja su corpus di binari noti (coreutils, busybox, openssl).

### 8.10 Fallback: Ghidra decompiler via FFI

Per binari dove il tuo decompiler ancora non performa bene (specialmente nei primi anni), integra il decompiler di Ghidra come fallback.

Architettura:
- Build standalone di Ghidra decompiler core (C++): esiste `ghidra_decompiler` standalone in `Ghidra/Features/Decompiler/src/decompile/cpp`.
- Compila come static lib.
- Wrap con C FFI in Rust.
- Input: function bytes + arch info + p-code Sleigh specs.
- Output: C-like pseudocode.

Crate: `rustre-decompiler-ghidra`. Mantieni come opzione attivabile da user.

## 9. Debugger nativo

### 9.1 Linux (ptrace)

Crate: `nix::sys::ptrace`.

API:

```rust
pub struct LinuxDebugger {
    pid: Pid,
    breakpoints: HashMap<Address, Breakpoint>,
    state: DebuggerState,
}

impl LinuxDebugger {
    pub fn attach(pid: Pid) -> Result<Self> {
        ptrace::attach(pid)?;
        let mut dbg = LinuxDebugger { /* ... */ };
        dbg.wait_for_stop()?;
        Ok(dbg)
    }
    
    pub fn launch(path: &Path, args: &[OsString]) -> Result<Self> {
        // fork + PTRACE_TRACEME + exec
        match unsafe { fork()? } {
            ForkResult::Child => {
                ptrace::traceme()?;
                Command::new(path).args(args).exec();
                unreachable!()
            }
            ForkResult::Parent { child } => {
                let mut dbg = LinuxDebugger { pid: child, /* ... */ };
                dbg.wait_for_stop()?;
                Ok(dbg)
            }
        }
    }
    
    pub fn read_memory(&self, addr: Address, len: usize) -> Result<Vec<u8>> {
        // process_vm_readv via libc — più veloce di PTRACE_PEEKDATA
        let mut buf = vec![0u8; len];
        let local = [IoSliceMut::new(&mut buf)];
        let remote = [RemoteIoVec { base: addr.0 as usize, len }];
        process_vm_readv(self.pid, &local, &remote)?;
        Ok(buf)
    }
    
    pub fn write_memory(&self, addr: Address, data: &[u8]) -> Result<()> {
        // process_vm_writev
    }
    
    pub fn get_registers(&self) -> Result<UserRegs> {
        ptrace::getregs(self.pid).map(|r| r.into())
    }
    
    pub fn set_registers(&self, regs: &UserRegs) -> Result<()> {
        ptrace::setregs(self.pid, regs.into())
    }
    
    pub fn step(&mut self) -> Result<StopReason> {
        ptrace::step(self.pid, None)?;
        self.wait_for_stop()
    }
    
    pub fn cont(&mut self) -> Result<StopReason> {
        // Re-enable breakpoint sull'IP corrente se necessario
        ptrace::cont(self.pid, None)?;
        self.wait_for_stop()
    }
    
    pub fn set_breakpoint(&mut self, addr: Address) -> Result<()> {
        // Save original byte
        let orig = self.read_memory(addr, 1)?[0];
        // Write INT3 (x86) / BRK #0 (ARM64)
        self.write_memory(addr, &[0xcc])?;
        self.breakpoints.insert(addr, Breakpoint { 
            kind: BreakpointKind::Software, 
            original_byte: orig, 
            enabled: true 
        });
        Ok(())
    }
    
    pub fn set_hw_breakpoint(&mut self, addr: Address, kind: HwBpKind) -> Result<()> {
        // Set DR0-DR3 via PTRACE_SETREGS on user_regs_struct (x86)
        // Or for ARM64: PTRACE_SETHBPREGS
    }
    
    pub fn wait_for_stop(&mut self) -> Result<StopReason> {
        let status = waitpid(self.pid, None)?;
        match status {
            WaitStatus::Stopped(_, sig) => {
                // Restore breakpoint byte if hit
                let pc = self.get_pc()?;
                if let Some(bp) = self.breakpoints.get(&Address(pc - 1)) {
                    self.write_memory(Address(pc - 1), &[bp.original_byte])?;
                    self.set_pc(pc - 1)?;
                    return Ok(StopReason::Breakpoint(Address(pc - 1)));
                }
                Ok(StopReason::Signal(sig))
            }
            WaitStatus::Exited(_, code) => Ok(StopReason::Exit(code)),
            // ...
        }
    }
}
```

Hardware breakpoints x86: DR0-DR3 (4 totali), DR7 control register definisce length/type per ognuno. Su ARM64: 4-16 hardware breakpoints + 4-16 watchpoints, varia per implementazione.

Multi-thread: `PTRACE_O_TRACECLONE` per intercettare creation thread, traccia tutti.

### 9.2 Windows (Debug API)

Crate: `windows-sys` per Win32 API.

```rust
pub struct WindowsDebugger {
    pid: u32,
    process_handle: HANDLE,
    threads: HashMap<u32, ThreadInfo>,
    breakpoints: HashMap<Address, Breakpoint>,
}

impl WindowsDebugger {
    pub fn launch(path: &Path, args: &[OsString]) -> Result<Self> {
        // CreateProcessW with DEBUG_ONLY_THIS_PROCESS or DEBUG_PROCESS
        let mut si: STARTUPINFOW = unsafe { std::mem::zeroed() };
        let mut pi: PROCESS_INFORMATION = unsafe { std::mem::zeroed() };
        si.cb = std::mem::size_of::<STARTUPINFOW>() as u32;
        
        let cmd_line = build_cmd_line(path, args);
        let cmd_line_wide: Vec<u16> = cmd_line.encode_utf16().chain([0]).collect();
        
        unsafe {
            CreateProcessW(
                std::ptr::null(),
                cmd_line_wide.as_ptr() as *mut _,
                std::ptr::null_mut(),
                std::ptr::null_mut(),
                FALSE,
                DEBUG_ONLY_THIS_PROCESS,
                std::ptr::null_mut(),
                std::ptr::null(),
                &mut si,
                &mut pi,
            );
        }
        
        Ok(WindowsDebugger {
            pid: pi.dwProcessId,
            process_handle: pi.hProcess,
            threads: HashMap::new(),
            breakpoints: HashMap::new(),
        })
    }
    
    pub fn wait_for_event(&mut self) -> Result<DebugEvent> {
        let mut event: DEBUG_EVENT = unsafe { std::mem::zeroed() };
        unsafe {
            WaitForDebugEvent(&mut event, INFINITE);
        }
        self.translate_event(event)
    }
    
    pub fn continue_event(&mut self, event: &DebugEvent, handled: bool) -> Result<()> {
        let status = if handled { DBG_CONTINUE } else { DBG_EXCEPTION_NOT_HANDLED };
        unsafe {
            ContinueDebugEvent(event.process_id, event.thread_id, status);
        }
        Ok(())
    }
    
    // ... ReadProcessMemory, WriteProcessMemory, GetThreadContext, SetThreadContext
}
```

Eventi importanti:
- `EXCEPTION_DEBUG_EVENT`: breakpoint hit (EXCEPTION_BREAKPOINT), single step (EXCEPTION_SINGLE_STEP), access violation, ecc.
- `CREATE_PROCESS_DEBUG_EVENT`: processo creato, info iniziale.
- `CREATE_THREAD_DEBUG_EVENT`: nuovo thread.
- `LOAD_DLL_DEBUG_EVENT`: DLL caricata. Salva module info, parse exports.
- `EXIT_*_DEBUG_EVENT`: terminazione.

WoW64 debugging (32-bit process su Windows 64-bit): usare `Wow64GetThreadContext` invece di `GetThreadContext`. Detect via `IsWow64Process`.

Hardware breakpoints: `Dr0-Dr7` in `CONTEXT` struct, identico a Linux ma via `GetThreadContext`/`SetThreadContext`.

### 9.3 macOS (mach)

Crate: `mach2`.

Mach kernel API: `task_for_pid`, `mach_vm_read`, `mach_vm_write`, `thread_get_state`, `thread_set_state`. Più complesso del Linux ptrace, anche perché:
- Hardened runtime + SIP limita debug di system binaries.
- Bisogna codesigning del debugger con entitlement `com.apple.security.cs.debugger`.
- iOS è effettivamente impossibile senza jailbreak.

Implementazione segue pattern simile a Linux ma con mach calls.

### 9.4 Remote debugging (GDB protocol)

Crate base: `gdbstub` (server-side, ma utile come reference) — adatta per client side.

Protocollo GDB remote: testuale, packet format `$<data>#<checksum>`. Operazioni:
- `?`: query stop reason
- `g`: read registers
- `G`: write registers
- `m<addr>,<len>`: read memory
- `M<addr>,<len>:<data>`: write memory
- `Z0,<addr>,<kind>`: set software breakpoint
- `z0,<addr>,<kind>`: remove
- `Z1,<addr>,<kind>`: hardware breakpoint
- `vCont;c`: continue all
- `vCont;s`: step
- `qSupported`: capabilities exchange

Implementazione client:

```rust
pub struct GdbRemoteDebugger {
    stream: TcpStream,
    arch: ArchHandle,
}

impl GdbRemoteDebugger {
    pub async fn connect(addr: SocketAddr, arch: ArchHandle) -> Result<Self> {
        let stream = TcpStream::connect(addr).await?;
        let mut dbg = GdbRemoteDebugger { stream, arch };
        dbg.handshake().await?;
        Ok(dbg)
    }
    
    async fn send_packet(&mut self, data: &str) -> Result<()> {
        let checksum: u8 = data.bytes().fold(0, |a, b| a.wrapping_add(b));
        let packet = format!("${}#{:02x}", data, checksum);
        self.stream.write_all(packet.as_bytes()).await?;
        // wait for '+' ack
        Ok(())
    }
    
    pub async fn read_memory(&mut self, addr: Address, len: usize) -> Result<Vec<u8>> {
        self.send_packet(&format!("m{:x},{:x}", addr.0, len)).await?;
        let response = self.recv_packet().await?;
        hex_decode(&response)
    }
    
    // ... altri metodi
}
```

Questo backend unlock: QEMU debugging, OpenOCD (JTAG hardware), gdbserver remoto, console emulators (Dolphin/RPCS3 con GDB stub), embedded firmware via probe.

### 9.5 Kernel debugging

Linux KGDB: usa il GDB remote backend sopra una serial / network connection con kernel compilato con KGDB support.

Windows kernel: protocollo KD (KdNet protocol per ethernet, KdCom per serial). Documentato pubblicamente da Microsoft. Implementazione complessa ma fattibile.

Hypervisor-level debugging: usa hypervisor (KVM/Hyper-V) con custom hooks per debug guest VM. Più avanzato, per il prodotto base lascia in seconda fase.

### 9.6 Dump analysis (WinDbg .dmp)

Minidump format documentato. Crate: `minidump-rs` (Mozilla).

Parsing:
- Minidump header
- Streams: Thread list, Module list, Memory list, Memory64 list, Exception info, System info, Handle data, ecc.
- Reconstruct memory: ogni Memory descriptor è una region readable.
- Build `MemoryProvider` su top.

ELF coredumps: parse via `goblin`, sezione `NT_PRSTATUS` per regs, `NT_PRPSINFO` per process info.

## 10. Time Travel Debugging (record + replay)

### 10.1 Background

TTD/Nirvana di Microsoft è il riferimento commerciale. `rr` di Mozilla è il riferimento open source su Linux. Paper chiave: Bhansali et al. "Framework for instruction-level tracing and analysis of program executions" (VEE 2006).

Idea base: registra tutto ciò che è non-deterministico (system calls, signals, async events, thread scheduling, RDTSC); il resto è puramente computazionale e replicabile. In replay, riproduci l'esecuzione deterministicamente.

### 10.2 Architettura

Due componenti:
1. **Recorder**: esegue il programma sotto controllo, intercetta non-determinism, lo registra.
2. **Replayer**: legge la trace, ricostruisce stato a ogni tick desiderato.

### 10.3 Recorder (Linux)

Approccio `rr`:
- ptrace + seccomp filter per intercettare ogni syscall.
- Single-thread on a single core (forza determinism scheduling).
- Per ogni syscall: registra args, return value, side effects (memoria scritta).
- Per signals: registra delivery point (PC + IP counter).
- Per RDTSC (intercettato via CPUID feature flag or via SIGSEGV on RDTSC instruction): registra valore.

```rust
pub struct Recorder {
    pid: Pid,
    trace_file: File,
    instr_counter: u64,         // via perf_event_open
    event_log: Vec<TraceEvent>,
}

#[derive(Serialize)]

    Syscall { 
        instr_count: u64, 
        nr: u32,

    Signal { instr_count: u64, sig: i32, info: SiginfoT },
    SchedSwitch { from_tid: u32, to_tid: u32, instr_count: u64 },
```

Issue critico: instruction counting deterministico. Usa `perf_event_open` con counter `PERF_COUNT_HW_INSTRUCTIONS` (hardware perf counter). Su CPU moderne ha alcuni pitfall: certain microops vs istruzioni, conteggio impreciso su alcuni eventi. `rr` ha workaround dettagliati — porta in Rust.

### 10.5 Reverse debugging UI

Da debugger view, comandi:
- "Step backward instruction"
- "Step backward over"
- "Reverse continue to breakpoint"
- "Go to tick N"
- "Find all writes to address X (in entire trace)"
- "Find all reads of address X"

L'ultimo è killer feature: in normale debug, sai che un valore è cambiato ma non quando/da chi. In TTD, query istantanea.

### 10.6 Cross-platform

Windows: il TTD Microsoft è closed ma può essere usato via WinDbg integration (file .run) — supporta lettura/parse di traces TTD esistenti (formato documentato esternamente in parte; ChakraCore TTD ha pubblicato dettagli; `ttd-bindings` esistono).

macOS: nessuna soluzione mature, replicate l'approccio rr ma su Mach API.

### 10.7 Emulator-based TTD (alternativa)

Se TTD nativo è troppo complesso per arch/OS specifici, usa emulazione Unicorn:
1. Esegui binario in Unicorn step by step.
2. Per ogni step, snapshot CPU state + memory deltas.
3. Trace è la sequenza di snapshots.
4. Replay = restore snapshot, step forward.

Slower ma sempre funziona. Usato come fallback per architetture esotiche.

## 11. Instrumentation runtime (Frida-equivalent)

### 11.1 Background

Frida è open source. Il core (`frida-gum`) fa hooking, scripting, stalking. Mantenuto da Ole André Vadla Ravnås e team. Per replicarlo:
1. Studia frida-gum sorgenti.
2. Implementa equivalenti in Rust.
3. Mantieni arms race contro nuovi OS aggiornandolo.

### 11.2 Componenti core

**Stalker** (instruction-level tracing): rewrite del codice in flight con instrumentation. Quando una funzione viene chiamata:
- Allochi un trampolino in memoria executable.
- Copia istruzioni della funzione nel trampolino, decoraNDOLE con callback before/after.
- Risolvi i branch (sostituisci target con punti nel trampolino).
- Sostituisci la prima istruzione della funzione originale con `jmp trampoline`.

**Interceptor** (function hooking): pattern classico:
- Inline hook: sostituisci primi N bytes con `jmp hook`. Stash bytes originali in trampoline che chiama back l'originale.
- IAT/PLT hook: modifica entries nella import table.
- VTable hook: modifica entries di vtable C++.
- Hardware breakpoint hook: usa DR0-DR3 + exception handler.

**Memory** (read/write target memory): in-process più semplice, out-of-process via OS API.

**Module enumerate** (lista DLL/dylib caricate): in-process via `dl_iterate_phdr` (Linux), `dyld_get_image_*` (macOS), `EnumProcessModules` (Windows).

### 11.3 Injection methods

Per attach a un processo esistente:

**Linux**:
- `LD_PRELOAD` sull'avvio (richiede launch).
- `ptrace`: PTRACE_ATTACH, allocate shellcode region via mmap syscall in target, write shellcode, execute, restore.
- `process_vm_*` + remote syscall execution.

**Windows**:
- `CreateRemoteThread` + `LoadLibrary`: classic injection.
- `NtMapViewOfSection`: modern, less detected.
- `SetWindowsHookEx`: solo per processi GUI.
- Manual mapping: bypassa Windows loader, mappa DLL manualmente.

**macOS**:
- `task_for_pid` + `mach_vm_*` + remote thread.
- Hardened runtime previene questo su system processes.

**Android**:
- `ptrace` come Linux.
- Frida-server installato come system service (richiede root).

**iOS**:
- Solo jailbroken: `task_for_pid` + injection.
- Su unjailbroken: solo se hai certificate signing per il target.

### 11.4 Scripting layer

Frida usa JavaScript via QuickJS o V8. Per replicare:
- Embed `rquickjs` (QuickJS Rust bindings) o `boa_engine` (pure Rust JS).
- Espone API JavaScript: `Interceptor`, `Memory`, `Module`, `Process`, `Thread`, `Stalker`, ecc.
- Script eseguito in-process nel target, comunica risultati via IPC (socket/pipe) al controller.

Alternativa più Rust-native: usa Lua o Rhai invece di JS. Pro: meno overhead. Contro: incompatibile con Frida scripts esistenti.

### 11.5 Anti-anti-debug toolkit (ScyllaHide-equivalent)

Ricette pubbliche per bypassare le anti-debug check più comuni. Implementa come "agents" attivabili:

- **PEB.BeingDebugged**: hook NtQueryInformationProcess(ProcessDebugPort=0).
- **PEB.NtGlobalFlag**: clear flag 0x70 in PEB.
- **CheckRemoteDebuggerPresent**: hook in user mode.
- **NtQueryInformationProcess(ProcessDebugObjectHandle)**: return invalid handle.
- **NtSetInformationThread(ThreadHideFromDebugger)**: hook, no-op.
- **OutputDebugStringA/W**: hook, doesn't trigger event.
- **GetLocalTime/QueryPerformanceCounter (timing checks)**: hook, return consistent deltas.
- **Hardware breakpoint detection (DR0-DR7 read via GetThreadContext on self)**: hook GetThreadContext, clear DR regs in returned context.
- **INT 2D / INT 1 / INT 3 manual detection**: SEH hook.
- **VirtualProtect on own code**: hook, allow always.
- **ProcessIoCounters / ProcessTimes**: normalize.

Pattern: dalla GUI, l'utente attiva i moduli che vuole prima dell'attach. Implementati come Frida-like agents in target process.

### 11.6 SSL/TLS pinning bypass (mobile use case)

Hook delle funzioni di certificate validation:
- **Android**:
  - `X509TrustManager.checkServerTrusted` → no-op
  - `SSLContext.init` con custom trust manager that accepts all
  - OkHttp `CertificatePinner.check` → no-op
  - Flutter (Dart): hook `BoringSSL` certificate verify
- **iOS**:
  - `SecTrustEvaluate` → kSecTrustResultProceed
  - `NSURLSession` delegate methods → return cert valid

Carica come pre-built scripts/agents bundled con la GUI.

## 12. Emulation (Unicorn + Qiling-style + shellcode)

### 12.1 Unicorn wrapper

Crate: `unicorn-engine`. Unicorn è basato su QEMU TCG, supporta x86/64, ARM/64, MIPS, SPARC, M68K, RISC-V.

```rust
    pub fn hook_code<F>(&mut self, range: AddressRange, callback: F) -> Result<HookId>

        let h = self.uc.add_code_hook(range.start.0, range.end.0, callback)?;
        Ok(HookId(h))
    }
    
    // hook_mem_read/write/invalid/fetch, hook_intr, hook_insn (SYSCALL/CPUID)
}
```

## 13. Symbolic execution & taint analysis

### 13.1 Background

Symbolic execution sostituisce values concreti con variabili simboliche, raccoglie path constraints, usa SMT solver per:
- Generare input che raggiungono path specifico
- Verificare unreachability
- Find inputs che fanno crash o triggerano vulnerability

Tools di riferimento open source: angr (Python), Triton (C++/Python), Manticore (Python), Miasm (Python). KLEE per LLVM IR.

### 13.2 Implementazione

```rust
pub struct SymbolicState {
    registers: HashMap<RegId, SymExpr>,
    memory: SymMemory,
    path_constraints: Vec<SymExpr>,
}

pub enum SymExpr {
    Const(u64, Size),
    Symbol(SymbolId, Size),
    Add(Box<SymExpr>, Box<SymExpr>),
    Sub(Box<SymExpr>, Box<SymExpr>),
    // ... tutte le ops LLIL ma simboliche
    Load { addr: Box<SymExpr>, size: Size },
    Ite { cond: Box<SymExpr>, then: Box<SymExpr>, else_: Box<SymExpr> },
}

pub struct SymExecEngine {
    states: Vec<SymbolicState>,    // active states (path exploration)
    solver: Z3Solver,
    arch: ArchHandle,
}

impl SymExecEngine {
    pub fn step(&mut self) -> Result<()> {
        // Pick a state (DFS / BFS / coverage-guided)
        let state = self.states.pop().unwrap();
        let instr = self.fetch_instr(state.pc())?;
        
        // Symbolic execution: lift a LLIL, applica ops simbolicamente
        let llil_ops = self.lift(&instr)?;
        for op in llil_ops {
            self.exec_symbolic(&mut state, op)?;
        }
        
        // Branching: se PC è simbolico (e.g. branch on symbolic cond), fork
        match self.resolve_pc(&state) {
            ResolvedPc::Concrete(addr) => {
                state.set_pc(addr);
                self.states.push(state);
            }
            ResolvedPc::Symbolic(cond) => {
                let mut state_t = state.clone();
                state_t.add_constraint(cond.clone());
                if self.solver.check(&state_t.path_constraints) {
                    state_t.set_pc(taken_addr);
                    self.states.push(state_t);
                }
                let mut state_f = state;
                state_f.add_constraint(cond.negate());
                if self.solver.check(&state_f.path_constraints) {
                    state_f.set_pc(not_taken_addr);
                    self.states.push(state_f);
                }
            }
        }
        Ok(())
    }
}
```

SMT solver backend: `z3-sys` (FFI a Z3) o `boolector` (più veloce per bitvectors).

Path explosion è il problema fondamentale. Mitigation:
- Path merging: state simili → uniscili con ITE.
- State pruning: rimuovi states sicuramente unreachable.
- Coverage-guided exploration.
- Heuristic ordering (DFS limitato in depth).

### 13.3 Taint analysis

Variante di symbolic execution dove non si traccia il valore esatto ma solo il "tainted bit". Più scalabile, meno preciso.

Usi:
- Detect data flow da input untrusted (network buffer) a sink dangerous (system call).
- Crash analysis: traccia da crash all'origin per capire vulnerability.

```rust
pub struct TaintedValue {
    taints: BitSet,  // bit set delle sorgenti tainting
}

pub struct TaintState {
    register_taints: HashMap<RegId, TaintedValue>,
    memory_taints: IntervalMap<Address, TaintedValue>,
}
```

Propagation rules: ADD, SUB, AND, OR, XOR propagano union dei taints degli operandi. LOAD/STORE propagano via memory.


## 15. PE triage e utilities

### 15.1 Detect It Easy clone

Detect packer/compiler/protector. Approccio:
- Database YAML/JSON di "signatures": pattern bytes + offset + condition + name.
- Scan PE: applica ogni signature, restituisci matches con confidence.

```yaml
- name: UPX 3.x
  type: packer

    - section: ".text"
      offset: 0
      bytes: "60 BE ?? ?? ?? ??"  # pushad + mov esi, imm32
    - section_name_present: "UPX0"
    - section_name_present: "UPX1"
  confidence: 95

  type: compiler
  match:
    - rich_header_contains: { product_id: 0x0104, build: 0x6228 }
  confidence: 99
```

Database iniziale: porta da DIE open source repo (database file separato).

### 15.2 Entropy analysis

Per ogni section: calcola Shannon entropy. Section con entropy > 7.5/8.0 likely packed/compressed/encrypted. Section "code" tipicamente 5-6.5.

Heatmap visualization: 1 pixel per N bytes, color from blue (low entropy) to red (high entropy).

### 15.3 Rich header analysis

Rich header è block prima del PE header che MSVC linker emette, contains product IDs + build numbers di tutti i componenti che hanno toccato il binario. È XOR'd con DanS key (visible). Pubblicly documented.

Parse rich header:
- Find "Rich" marker before PE header
- XOR key è qword precedente
- Decode entries: (product_id, build_number, count) tuples
- Map product_id ai compilers/linkers/tools noti

Util per:
- Compiler fingerprinting (preciso a build number)
- Malware lineage (campioni dello stesso threat actor hanno rich header simili)
- Filter false positives in similarity

### 15.4 CFF Explorer equivalent (PE editor)

Pannello UI:
- Tree view: DOS Header, NT Headers (File Header, Optional Header), Sections, Data Directories (Import, Export, Resource, Exception, Security, Reloc, Debug, TLS, Load Config, IAT, Delay Import, COM Descriptor).
- Per ogni node: form editor con field labels, descriptions, current values.
- Edit any field → applica patch al PE.
- Hex view sincronizzato (highlight di bytes attuali del field).

Sezioni speciali:
- Resource tree: navigazione gerarchica (type → name → language → data), edit possible.
- Import table: aggiungi/rimuovi imports, modify ordinals.
- Export table: similar.

Operations:
- Recalculate PE checksum.
- Apply random/custom section padding.
- Set entry point.
- Modify ImageBase.
- Strip debug info.
- Add new section.

### 15.5 Scylla equivalent (IAT rebuild + dump)

Use case classico: malware unpacked è in memoria, vuoi dump-arlo a un PE valido.

Step:
1. **Dump**: read process memory da ImageBase, length = ImageSize.
2. **Section alignment**: rebuild section table dal memory layout (sezioni stanno a section_alignment, non file_alignment, in memoria).
3. **IAT detection**: scansiona la memoria di processo cercando array di pointers che pointano in DLL system. Identifica IAT del binario unpacked.
4. **IAT reconstruction**: per ogni entry IAT, risolvi DLL + function name leggendo memory delle DLL caricate.
5. **PE patching**: scrivi nuova import directory, aggiorna IAT pointer.
6. **OEP detection**: Original Entry Point dell'unpacked binary. Heuristics:
   - Hook su VirtualAlloc/VirtualProtect, OEP è dopo l'ultima alloc che marca PE_RWX
   - Detect "memory access to unmapped region followed by mapping at fixed address"
   - User-set via debugger (manuale dopo unpacking)

Output: PE eseguibile riapribile in IDA/Ghidra senza il packer.

## 16. Binary diffing (BinDiff/Diaphora-equivalent)

### 16.1 Algoritmi base (Flake 2004 / Dullien-Rolles 2005)

**Step 1 — Function matching**: per ogni funzione in binario A, trova match in B.

Tecniche di matching iniziali (high confidence):
1. **Name matching**: stesso nome → match.
2. **Hash matching**: stesso bytes esatti → match.
3. **Edge tuple hash**: hash di (count_in_edges, count_out_edges, count_basic_blocks) → strong indicator.
4. **MD-Index**: paper Halvar Flake. Hash di:
   - in-degree
   - out-degree
   - topology hash (basic blocks + edges)
   - prime-product based hash

**Step 2 — Propagation**: una volta matched alcune funzioni con alta confidence, propaga matching ai vicini.
- Se f_A matches f_B, e f_A calls g_A, g_B is called by f_B, e g_A/g_B hanno strutture simili → match g_A/g_B.

**Step 3 — Basic block matching** (dentro funzioni matched): per ogni BB in f_A, find best BB in f_B usando:
- Topology hash (CFG locale around the BB)
- Instruction count, mnemonic histogram
- Constants matching
- Call targets matching (functions matched)

**Step 4 — Instruction matching** (dentro BB matched): instruction-by-instruction, identical or "similar" (differenti operandi ma stessa mnemonic).

### 16.2 Hungarian algorithm enhancement (BinSlayer)

Per migliorare matching, BinSlayer (2013) usa Jonker-Volgenant assignment algorithm su matrice di similarity scores.

```rust
fn match_functions(funcs_a: &[FunctionInfo], funcs_b: &[FunctionInfo]) -> Vec<Match> {
    let n = funcs_a.len();
    let m = funcs_b.len();
    let mut cost = vec![vec![0.0; m]; n];
    
    for i in 0..n {
        for j in 0..m {
            cost[i][j] = -similarity(&funcs_a[i], &funcs_b[j]);
            // Negative because Hungarian minimizes cost (we want maximum similarity)
        }
    }
    
    let assignment = hungarian_algorithm(&cost);
    assignment.into_iter()
        .map(|(i, j)| Match { 
            a: funcs_a[i].id, 
            b: funcs_b[j].id, 
            score: -cost[i][j] 
        })
        .filter(|m| m.score > THRESHOLD)
        .collect()
}
```

### 16.3 Semantic diffing (oltre struttura)

Limitazione di BinDiff: confronta strutturalmente, non semanticamente. Due funzioni che fanno la stessa cosa scritte diversamente non matcheranno.

Approccio semantico (SemDiff paper, 2017):
- Symbolically execute entrambe le funzioni.
- Compare output constraints/effects.
- Match if semantically equivalent.

Costoso ma utile per patch analysis su funzioni piccole.

### 16.4 UI

Pannello "Diff Result":
- Pane sinistra: funzioni binario A
- Pane destra: funzioni binario B
- Linee tra: match con color (green=identical, yellow=similar, red=changed)
- Sotto: side-by-side disassembly/decompiler view delle due funzioni matched

Use cases:
- Patch diffing (find what changed in CVE patch)
- Malware variant comparison
- License compliance (verify forks)

## 17. FLIRT-style function signatures

### 17.1 Idea base

Le static library functions (CRT, libc, stl, ecc.) appaiono in moltissimi binari uguali. Riconoscerle automaticamente e rinominarle elimina enorme rumore dall'analisi.

FLIRT (Fast Library Identification and Recognition Technology) di Hex-Rays è documentato in articoli ufficiali:
- Pattern di bytes con parts "fissi" e parts "variabili" (immediate values, relocations).
- Trie data structure per match veloce.
- Disambiguation via CRC16 di bytes successivi quando match parziale.

### 17.2 Signature generation

Da una static library (.lib su Windows, .a su Unix):
1. Estrai object files (.obj/.o).
2. Per ogni funzione esportata:
   - Disassembla bytes.
   - Identifica relocations (immediate values che il linker risolve) → mark come "wildcard" in signature.
   - Genera signature: bytes con wildcards.
3. Aggrega per length: signatures lunghe in trie principale, signatures corte usano "secondary check".
4. Calcola CRC16 di porzione dopo prefisso fisso per disambiguation.

```rust
pub struct FlirtSignature {
    pub name: String,
    pub library: String,
    pub bytes: Vec<u8>,
    pub mask: Vec<u8>,        // 1 = match esatto, 0 = wildcard
    pub crc16: Option<u16>,
    pub crc_offset: usize,
    pub crc_length: usize,
    pub referenced_names: Vec<(usize, String)>,  // names referenced by relocations
}
```

### 17.3 Trie structure per fast lookup

```rust
pub struct FlirtTrie {
    root: TrieNode,
}

pub struct TrieNode {
    branches: HashMap<u8, Box<TrieNode>>,
    wildcard_branch: Option<Box<TrieNode>>,
    leaves: Vec<FlirtSignature>,
}

impl FlirtTrie {
    pub fn lookup(&self, bytes: &[u8]) -> Vec<&FlirtSignature> {
        let mut matches = vec![];
        self.lookup_recursive(&self.root, bytes, 0, &mut matches);
        // Filter via CRC16 check
        matches.into_iter()
            .filter(|sig| self.crc_check(sig, bytes))
            .collect()
    }
}
```

### 17.4 Application a un binario

Per ogni funzione detected nel binario:
1. Estrai bytes.
2. Query trie con i primi N bytes.
3. Match candidates → verify CRC16.
4. Se match unico: rinomina funzione, applica type info se in signature.
5. Se multiple matches: registra come "ambiguous", lascia all'utente decidere.

### 17.5 Signature database building

Build signatures da:
- Visual Studio CRT (.lib files in Visual Studio install).
- glibc, musl, uClibc (compile .a archives).
- Common open source libs (zlib, openssl, libpng, ecc.).
- Rust std (compile release artifacts).
- Boost, Qt, MFC.

Output: collezione di .sig files per target compiler + version + arch.

Distribuisci con il tool come "library packs" scaricabili.

## 19. Fuzzing (AFL++ / libFuzzer / Boofuzz equivalent)

### 19.1 Coverage-guided fuzzing (AFL++-style)

Componenti core:
- **Mutator**: prende un input, produce variations (bit flips, byte mutations, splicing, dictionary insertion, havoc, ecc.).
- **Executor**: lancia il target con l'input, raccoglie coverage.
- **Queue**: corpus di inputs interessanti, sorted by novelty (new coverage).
- **Scheduler**: scegli quale input mutare next (favors inputs that produce new coverage).

```rust
pub struct AflFuzzer {
    target: TargetExecutor,
    queue: InputQueue,
    coverage: CoverageMap,
    mutator: Box<dyn Mutator>,
    stats: FuzzerStats,
    crashes: CrashCollection,
}

pub trait TargetExecutor: Send + Sync {
    fn execute(&mut self, input: &[u8]) -> Result<ExecutionResult>;
}

pub struct ExecutionResult {
    pub status: ExecutionStatus,
    pub coverage_bits: BitVec,
    pub execution_time: Duration,
}

pub enum ExecutionStatus {
    Normal,
    Crash { signal: i32, fault_addr: Option<Address> },
    Timeout,
    Hang,
}

impl AflFuzzer {
    pub fn run_iteration(&mut self) -> Result<()> {
        // 1. Select input from queue
        let input = self.queue.select(&mut self.scheduler);
        
        // 2. Mutate
        let mutated = self.mutator.mutate(&input.data);
        
        // 3. Execute
        let result = self.target.execute(&mutated)?;
        
        // 4. Check for new coverage
        let new_bits = self.coverage.update(&result.coverage_bits);
        
        // 5. Save interesting input
        if new_bits > 0 {
            self.queue.add(Input { data: mutated, ..Default::default() });
        }
        
        // 6. Save crash if interesting
        if matches!(result.status, ExecutionStatus::Crash { .. }) {
            self.crashes.add(mutated, result);
        }
        
        Ok(())
    }
}
```

Instrumentation di coverage:
- **Compile-time**: clang -fsanitize-coverage=trace-pc-guard (libFuzzer-compatible) o AFL_USE_PERSISTENT.
- **Binary-only**: QEMU mode (AFL's qemuafl), DynamoRIO instrumentation, intel-pt hardware tracing.

Per `rustre-fuzz-afl` Rust-native: compile-time via custom LLVM pass + run-time tracking via shared mem bitmap (come AFL).

### 19.2 libFuzzer-style (in-process)

Fuzzing in-process è più veloce (no fork+exec per ogni iteration).

```rust

    fn run(&mut self, input: &[u8]) -> FuzzResult;
}

    target: T,
    // ... coverage, queue, mutator
}
```

L'utente scrive:
```rust

```

Linker tricks: la funzione `fuzz_target` viene compilata con sanitizer coverage. Crash → segfault handler interno raccoglie info, salva crash, continua fuzzing.

### 19.3 Mutators

Library di mutators:
- **Bit flip**: flip 1-4 bit consecutivi.
- **Byte flip**: flip 1-32 bit consecutivi (aligned).
- **Arithmetic**: ±1..±35 su byte/word/dword.
- **Interesting values**: lista hard-coded di interesting int values (0, 1, -1, INT_MAX, ecc.).
- **Dictionary insertion**: inserisci magic strings/numbers da dictionary.
- **Splicing**: combina due inputs.
- **Havoc**: random combinations of multiple mutations.
- **Structure-aware mutators**: per format-aware fuzzing (es. PNG, ELF), preserve structural validity.

### 19.4 Sanitizers (ASAN/UBSAN equivalents)

Detect runtime bugs:
- **AddressSanitizer**: heap overflow, use-after-free, double-free. Implementation: shadow memory (1 byte shadow per 8 bytes real), redzones around allocations, quarantine on free.
- **UndefinedBehaviorSanitizer**: signed integer overflow, null deref, misaligned access, divide by zero. Implementation: compile-time instrumentation che inserisce check.
- **ThreadSanitizer**: data races. Happens-before tracking.
- **MemorySanitizer**: uninitialized reads. Bit-level taint tracking.

In Rust per binari compilati da source: sfrutta i sanitizers già esistenti in rustc/LLVM. Per binary-only fuzzing: Memory error detection via QEMU plugins (qasan), Valgrind-style.

```yaml
      - { name: password, type: cstring, fuzz: true }
```

Fuzzer evolve messages mutating fields marked `fuzz: true`, checking server responses + crashes.

## 20. Deobfuscation

Obiettivo: replicare D-810 (plugin Hex-Rays), OLLVM-deobfuscator, de4dot per .NET, deobfuscator generico per JavaScript/Lua. Funziona a livello MLIL/HLIL come passes di analisi.

### 20.1 Architettura

Crate `rustre-deobf`:
```rust
pub trait DeobfPass {
    fn name(&self) -> &str;
    fn applies_to(&self, func: &MlilFunction) -> bool;
    fn run(&self, func: &mut MlilFunction, ctx: &mut PassContext) -> DeobfResult;
}

pub struct DeobfPipeline {
    passes: Vec<Box<dyn DeobfPass>>,
    max_iterations: usize,  // run until fixpoint
    timeout: Duration,
}

impl DeobfPipeline {
    pub fn run(&self, func: &mut MlilFunction) -> Report {
        let mut changed = true;
        let mut iter = 0;
        while changed && iter < self.max_iterations {
            changed = false;
            for pass in &self.passes {
                if pass.applies_to(func) {
                    let result = pass.run(func, &mut ctx);
                    if result.modified { changed = true; }
                }
            }
            iter += 1;
        }
    }
}
```

### 20.2 Pass: Opaque Predicate Removal

Predicato opaco: condizione la cui valutazione è costante ma il compiler non lo vede. Es: `if ((x*x*x - x) % 6 == 0)` è sempre vero per ogni x intero.

Tecnica: per ogni branch condizionale, lancia symbolic execution sul predicato con Z3:
```rust
fn is_opaque(condition: &MlilExpr, ctx: &SymExecCtx) -> Option<bool> {
    let sym_expr = lift_to_z3(condition, ctx);
    let solver = Solver::new(&ctx.z3);
    // controlla soddisfacibilità di TRUE e FALSE
    solver.assert(&sym_expr.eq(&ctx.z3.from_bool(false)));
    let can_be_false = solver.check() == SatResult::Sat;
    solver.reset();
    solver.assert(&sym_expr.eq(&ctx.z3.from_bool(true)));
    let can_be_true = solver.check() == SatResult::Sat;
    match (can_be_true, can_be_false) {
        (true, false) => Some(true),    // sempre vero
        (false, true) => Some(false),   // sempre falso
        _ => None,                       // genuino
    }
}
```

Se opaco → rimpiazza branch con jump diretto al ramo sempre preso, elimina dead branch.

### 20.3 Pass: Control Flow Flattening Removal

CFF (visto in OLLVM, Tigress, .NET ConfuserEx): tutto il control flow originale è sostituito da uno switch su una variabile di stato:
```c
while (state != EXIT) {
    switch (state) {
        case 1: ...; state = 5; break;
        case 5: ...; state = 9; break;
        ...
    }
}
```

Algoritmo de-flattening (basato su Quarkslab paper "Defeating eXtreme Obfuscation" + miasm tradition):
1. Identifica il "dispatcher": basic block con switch su variabile di stato (state variable)
2. Identifica i "real blocks": blocchi raggiungibili dal dispatcher che modificano la state variable
3. Costruisci il "state transition graph": symbolic execution di ogni real block per determinare il valore della state variable in uscita (può essere costante o condizionale)
4. Ricostruisci CFG originale: ogni real block punta direttamente ai successori reali (saltando dispatcher)
5. Elimina dispatcher + state variable

```rust
pub struct CffDeobfuscator;

impl DeobfPass for CffDeobfuscator {
    fn run(&self, func: &mut MlilFunction, ctx: &mut PassContext) -> DeobfResult {
        let dispatcher = find_dispatcher(func)?;
        let state_var = identify_state_variable(&dispatcher, func)?;
        let real_blocks = find_real_blocks(func, state_var)?;
        let mut transition_graph = HashMap::new();
        for &bb in &real_blocks {
            let next_states = symex_state_var(func, bb, state_var, ctx)?;
            transition_graph.insert(bb, next_states);
        }
        rewrite_cfg(func, &transition_graph)?;
        eliminate_dead(func)?;
        DeobfResult::modified()
    }
}
```

### 20.4 Pass: MBA (Mixed Boolean-Arithmetic) Simplification

MBA: espressioni tipo `(x ^ y) + 2*(x & y)` che equivale a `x + y`. Usata pesantemente da Themida, VMProtect, Tigress.

Tecnica primaria: pattern matching su forme canoniche note (tabella di ~200 identità MBA dalla letteratura, principalmente paper di Eyrolles "Defeating MBA Obfuscation"):
```rust
const MBA_PATTERNS: &[(&str, &str)] = &[
    ("(x ^ y) + 2*(x & y)", "x + y"),
    ("(x | y) - (x & y)", "x ^ y"),
    ("(x & y) + (x | y)", "x + y"),
    ("-(~x)", "x + 1"),
    ("~(x - 1)", "-x"),
    // ... ~200 patterns
];

fn match_mba(expr: &MlilExpr) -> Option<MlilExpr> {
    for (pattern, replacement) in MBA_PATTERNS {
        let p = parse_pattern(pattern);
        if let Some(bindings) = pattern_match(expr, &p) {
            return Some(instantiate(replacement, &bindings));
        }
    }
    None
}
```

Tecnica secondaria (per pattern unknown): **SiMBA** algorithm (Reichenwallner & Meerwald-Stadler 2022). Estrae espressioni MBA da `n` variabili, le valuta su tutti i 2^n vettori binari, costruisce vettore "truth table" → cerca espressione bitwise più semplice equivalente:
```rust
fn simba_simplify(expr: &MlilExpr, vars: &[Var]) -> Option<MlilExpr> {
    let n = vars.len();
    if n > 4 { return None; }  // truth table cresce 2^n
    let mut truth = vec![0u64; 1 << n];
    for assignment in 0..(1u64 << n) {
        let mut env = HashMap::new();
        for (i, v) in vars.iter().enumerate() {
            env.insert(v.clone(), (assignment >> i) & 1);
        }
        truth[assignment as usize] = eval_expr(expr, &env);
    }
    espresso_minimize(&truth, vars)  // logic minimization
}
```

Tecnica terziaria (per casi residui): Z3 equivalence check con candidate simplifications da una grammar:
```rust
fn z3_simplify(expr: &MlilExpr, max_size: usize) -> Option<MlilExpr> {
    for candidate in enumerate_candidates(max_size) {
        if z3_prove_equivalent(expr, &candidate) {
            return Some(candidate);
        }
    }
    None
}
```

### 20.5 Pass: String Deobfuscation

Stringhe spesso decryptate runtime: ogni accesso a stringa è preceduto da una piccola funzione che decrypta in memoria. Identifica funzioni "string decoder":

```rust
fn find_string_decoders(bv: &BinaryView) -> Vec<FunctionRef> {
    let candidates = bv.functions().filter(|f| {
        f.basic_blocks().count() < 5
            && f.has_loop()
            && f.calls_count() == 0
            && f.has_byte_xor_or_arithmetic()
            && f.has_caller_with_constant_string_pointer_arg()
    }).collect();
    candidates
}

fn extract_strings_via_emulation(decoder: &Function, bv: &BinaryView) -> Vec<DecodedString> {
    let mut out = Vec::new();
    for call_site in decoder.callers() {
        let args = recover_call_args(call_site, bv);
        let mut emu = UnicornEmu::new(bv.arch());
        emu.map_memory(bv);
        emu.set_args(&args);
        emu.run_function(decoder.address())?;
        let result_ptr = emu.read_return_value();
        if let Some(s) = emu.read_cstring(result_ptr) {
            out.push(DecodedString { addr: call_site, value: s });
        }
    }
    out
}
```

Annota le call site nel KG: `(InstructionRef)-[DECODED_STRING]->(StringNode)` così l'utente vede la stringa decryptata inline nel decompiler view.

### 20.6 Pass: VM-based Obfuscation (VMProtect, Themida, etc.)

VM obfuscation: codice originale è tradotto in bytecode per una VM custom, e il binario contiene VM dispatcher + handler. Per de-obfuscare:

1. **Trova VM dispatcher**: tipicamente switch enorme su un opcode byte, o computed jump tramite handler table
2. **Identifica handlers**: blocchi di codice raggiunti dal dispatcher
3. **Lift each handler to MLIL**: ogni handler implementa una "VM instruction"
4. **Inferisci semantica handler**: tramite simbolic execution determina quale operazione esegue ognuno (e.g., "carica costante da bytecode stream e push su VM stack")
5. **Costruisci VM ISA descriptor**: struttura dati che descrive l'ISA della VM
6. **Disassembla bytecode con quell'ISA**: ora hai instruction stream "VM-level"
7. **Lift VM instructions to MLIL standard**: traduce ogni VM op a sequenza MLIL nativa
8. **Run standard analysis on lifted MLIL**: come se fosse codice normale

```rust
pub struct VmDeobfuscator {
    detector: VmDispatcherDetector,
    semantic_inferrer: HandlerSemanticInferrer,
}

impl VmDeobfuscator {
    pub fn deobfuscate(&self, func: &Function, bv: &BinaryView) -> Option<LiftedFunction> {
        let dispatcher = self.detector.find(func)?;
        let handlers = self.detector.find_handlers(&dispatcher)?;
        let mut isa = VmIsa::new();
        for h in &handlers {
            let sem = self.semantic_inferrer.infer(h, bv)?;
            isa.add_handler(h.opcode, sem);
        }
        let bytecode_region = identify_bytecode(func, &dispatcher, bv)?;
        let vm_instructions = isa.disassemble(&bytecode_region);
        let lifted = isa.lift_to_mlil(&vm_instructions);
        Some(lifted)
    }
}
```

Questo è ricerca attiva (Tigress challenges, paper come "Synthesis of Adversarial DNNs", "VMAttack", ecc.). Non aspettarti automazione perfetta su VMProtect 3.x. Però ottimi risultati su VM custom semplici, frequenti in malware moderno e in protezioni anti-tamper di software commerciale.

### 21.4 MITM Proxy (Burp-style + mitmproxy-style)

### 25.3 Smali Output

### 25.4 Dalvik → Java Decompiler (JADX-Equivalent)

Pipeline:
1. **Dalvik → IR**: lift Dalvik instructions a LLIL adattato (registers, type tags). Dalvik è già register-based quindi più semplice di stack-based JVM.
2. **SSA**: classico SSA construction sul method
3. **Type inference**: Dalvik è weakly typed, propaga tipi forward dai parameter/field types
4. **Control flow structuring**: stessa logica DREAM/Phoenix-style della sezione 5 — Dalvik è high-level abbastanza che gli pattern producono Java naturale
5. **Expression reconstruction**: ricostruisci espressioni Java da sequenze register-based
6. **Generic recovery**: dalle signature strings (`Ljava/util/List<Ljava/lang/String;>;`) recupera generics
7. **Lambda / synthetic recovery**: pattern di classi `$Lambda$N` generate da javac → fold a lambda expression
8. **Annotation parsing**: dalle `dalvik.annotation.*` metadata
9. **Inner class recovery**: dai naming patterns + outer references
10. **Emit Java source**

```rust
pub struct DexDecompiler {
    options: DecompileOptions,
}

impl DexDecompiler {
    pub fn decompile_method(&self, m: &EncodedMethod, ctx: &DexContext) -> Result<String> {
        let il = lift_dalvik(m)?;
        let ssa = construct_ssa(il)?;
        let typed = infer_types(ssa, ctx)?;
        let structured = structure_cfg(typed)?;
        let expressions = reconstruct_expr(structured)?;
        emit_java(expressions, ctx)
    }
}
```

JADX è ~250K righe Java. Reimplementarlo in Rust è 100-150K righe. AI-parallelizzabile sui passes, ma il quality bar lo decide il corpus di test reali.

### 27.4 CIL → C# Decompiler

CIL è alto-livello (stack-based con tipi typed), il decompiler è più simile a un disassembler-pretty-printer + control flow restructuring + pattern recognition:

1. **Stack-to-register**: trasforma stack-based in register-based (ogni stack slot diventa una variabile). CIL ha info esatte di stack depth a ogni instruction.
2. **Type tracking**: ogni stack slot ha tipo noto da metadata
3. **Control flow structuring**: stesso framework della sezione 5
4. **Pattern recognition**: foreach loops, lambda capture, async/await state machines (compilatore C# genera state machine class con `MoveNext` switch su `<>1__state` — pattern decompile a `async`/`await`), LINQ query expressions, properties (`get_X` / `set_X` ↔ `X { get; set; }`), events (`add_X` / `remove_X`), generic instantiations
5. **String literal recovery** da `#US` stream
6. **Custom attribute decoding** da `#Blob` stream
7. **Emit C# source**

Reference: ILSpy decompiler (open source MIT) ha ~150K righe C# che fanno esattamente questo. Studiabile direttamente, non è closed-source. Reimplementare in Rust: ~80-120K righe AI-assistite.

```rust

    pub fn decompile_method(&self, m: &MethodDef, assembly: &AssemblyFile) -> Result<String>;
    pub fn decompile_assembly(&self, assembly: &AssemblyFile) -> Result<HashMap<String, String>>;
}
```

### 27.5 Assembly Editor (dnSpy-Style)

Edit + save funzionalità: modifica IL, salva nuovo PE. Steps:
- Re-serializza tables modificate (con re-encoding di stream `#Blob`, `#US`, `#Strings`, `#GUID`)
- Genera nuovo `IMAGE_COR20_HEADER`
- Aggiorna PE headers (size, checksums)
- Re-firma se necessario (re-strong-naming se utente fornisce key)

Editor GUI: tree view dell'assembly, click su method → opens C# decompiled view ed CIL view (sync), edit any view, recompile-on-save (C# edit triggers Roslyn compile-to-CIL via Roslyn-CSharp ↔ Rust binding, oppure mantieni CIL editing diretto).

### 27.6 De-obfuscation (de4dot Equivalent)

de4dot supporta ~30 obfuscators commerciali/free .NET. Pattern per ognuno:
- **Confuser/ConfuserEx**: control flow flattening, anti-tamper, anti-debug, reference proxy, constant encryption
- **Eazfuscator.NET**: string encryption con runtime decryption + virtualization
- **.NET Reactor**: similar mix
- **SmartAssembly**: name mangling, MSIL obfuscation
- **Skater .NET, Spices.NET, Crypto Obfuscator, Babel, ecc.**

Per ognuno: detector (fingerprint via metadata patterns + attribute presence + obfuscator-specific markers) + cleaner (rimuove pattern specifico, decifra string, unflatten CFG).

Stesso framework `DeobfPass` della sezione 20, ma applicato a CIL invece di MLIL nativo.

### 27.7 Resource Extraction

`.resources` files embedded: parser BinaryFormat per estrarre embedded strings, images, ecc.

### 27.8 AOT-compiled .NET (NativeAOT / Mono AOT / IL→C++ frameworks)

Tre famiglie:
- **NativeAOT (.NET 7+)**: il C# è compilato direttamente a native code via Reflection-Free pipeline. Metadata embedded ma in forma ridotta (no full reflection). Reader specializzato che estrae il subset disponibile.
- **IL→Native via C++ transpilation**: alcuni framework compilano IL ad altro linguaggio intermedio (C++) e poi a native con compiler ottimizzante. Il C# originale non è recuperabile direttamente dal binary nativo — bisogna parsare il metadata sidecar (file `global-metadata.dat` o equivalente) e correlarlo al binary nativo per ricostruire type system, signatures, e potenzialmente lifftare il C++/asm generato a una forma C#-like. Implementazione: parser metadata sidecar (~3000 righe) + correlator binary↔metadata → ricostruzione type system. Pipeline generica, indipendente da specifico vendor.
- **Mono AOT**: ibrido che pre-compila parti dell'IL a native ma mantiene il framework Mono runtime. Gestito separatamente: identificare quali method sono AOT e quali rimangono JIT-compiled runtime.

### 30.6 Auth & Security

MCP transport:
- **stdio**: no auth, local only
- **HTTP/SSE/WS**: bearer token configurabile, opzionalmente mutual TLS
- **Unix socket**: filesystem perms

Tools sensibili (debug.attach con escalation, sandbox.submit con execution) richiedono confirmation step esplicito in modalità interactive. In modalità non-interactive (CI), confirmation è bypassata se config flag impostato.

## 31. AI Agent Integration

### 31.1 Filosofia

Tre livelli di AI integration:
1. **Inline assist**: AI suggerisce nomi variabili/funzioni, types, commenti dal contesto del decompiler
2. **Conversational**: chat panel docked dove utente fa domande sul binary, AI risponde usando i tool MCP della suite
3. **Autonomous workflows**: agenti che eseguono catene di analisi (es. "analizza questo malware completamente": triage → static analysis → sandbox → IOC extraction → MISP push)

### 31.7 Fine-Tuning Pipeline (Opzionale)

Per costruire modelli specializzati in RE che migliorano qualità delle suggestion AI:
- **Dataset**: pull funzioni decompilate (con e senza simboli) da binari open source compilati con build pipelines reproducibili (Debian unstripped repos, sourceware, GitHub Actions builds dei progetti popolari). Pipeline scriptata: per ogni binary, run analisi completa su versione stripped, capture decompiler output, target è il nome reale dalla versione unstripped.
- **Auto-labeling**: function name come target, decompiled stripped code come input. Variants: variable naming, function summary, type inference, vulnerability hypothesis.
- **Base models**: Qwen3-Coder-30B, DeepSeek-Coder-V2, StarCoder2, CodeLlama. LoRA fine-tune con `peft` + `transformers` (Python sidecar pipeline) o `candle` (Rust native, alternativa).
- **Hosting**: vLLM (Python) o `candle`/`mistral.rs` (Rust native, no Python dependency) per inference local. Una GPU consumer-grade (16-24GB VRAM) è sufficiente per LoRA inference su modelli 7-13B.
- **Evaluation**: held-out test set di binari con simboli, metriche BLEU/CodeBLEU/exact-match su function names, edit distance su variable names, qualitative review umana su sample stratificato.

Lo stesso framework si estende a: variable naming, summary generation, vulnerability detection, exploit primitive identification, malware family classification, behavioral fingerprinting.

Crate `rustre-agent-finetune` (opzionale, non shipped per default): script + utility per costruzione dataset + LoRA training + evaluation harness.

### 32.3 Reactive State

GPUI usa entity model: ogni view è un `Entity<T>` con state mutabile via `cx.update_entity(|state, cx| ...)`. State changes trigger automatic re-render.

```rust
pub struct DisassemblyView {
    binary: Entity<BinaryView>,
    current_address: Address,
    selected_address: Option<Address>,
    annotations: HashMap<Address, Annotation>,
    scroll: ScrollState,
}

impl Render for DisassemblyView {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        let instructions = self.binary.read(cx).window_around(self.current_address, 1000);
        div()
            .flex()
            .flex_col()
            .child(self.render_header(cx))
            .children(instructions.into_iter().map(|i| {
                self.render_instruction(i, cx)
            }))
            .on_action(cx.listener(Self::handle_keystroke))
    }
}
```

## 33. Plugin System

### 33.1 Architettura

Plugin = libreria dinamica (`.so`/`.dll`/`.dylib`) che implementa trait `Plugin`. Sandboxed per default (no FS/network access unless requested in manifest).

```rust
#[no_mangle]
pub extern "C" fn rustre_plugin_init() -> Box<dyn Plugin> {
    Box::new(MyPlugin::new())
}

pub trait Plugin: Send + Sync {
    fn manifest(&self) -> PluginManifest;
    fn init(&mut self, ctx: &mut PluginContext) -> Result<()>;
    fn shutdown(&mut self);
}

pub struct PluginManifest {
    pub name: String,
    pub version: Version,
    pub author: String,
    pub description: String,
    pub min_api_version: ApiVersion,
    pub permissions: Vec<Permission>,
    pub extension_points: Vec<ExtensionPoint>,
}

pub enum Permission {
    FsRead(Vec<PathBuf>),
    FsWrite(Vec<PathBuf>),
    Network(Vec<NetworkScope>),
    Subprocess(Vec<String>),  // allowed commands
    UnsafeFfi,                // explicit opt-in
}
```

### 33.2 Extension Points

Plugin si registra a uno o più extension points:
- `Loader`: parser per formato binario nuovo
- `Architecture`: ISA nuova
- `AnalysisPass`: pass MLIL/HLIL
- `DeobfPass`: pass deobfuscation
- `Dissector`: protocollo di rete
- `MemPlugin`: plugin memory forensics
- `Decompiler`: backend decompiler alternativo
- `Theme`: tema UI
- `Action`: comando menubar/context-menu
- `View`: panel UI custom
- `McpTool`: tool MCP custom
- `Workflow`: workflow predefinito
- `IntelProvider`: provider threat intel
- `LlmBackend`: backend LLM custom

### 33.3 Plugin API Stability

`rustre-plugin-api` crate: contiene SOLO i trait/struct esposti ai plugin, versionato semver. Crate principale dipende da `rustre-plugin-api`. Plugin compilati contro `rustre-plugin-api = "X.Y"` funzionano con qualunque app `X.*` (minor compat).

ABI: poiché Rust non ha ABI stable, usiamo:
- `abi_stable` crate per i tipi di confine
- O più semplicemente, plugin compilati con la STESSA versione del compiler dell'app principale (più rigido ma più safe)
- Documentazione chiara: distribuire plugin = distribuire binary + compatibility table

### 33.4 Scripting Layer (Rhai / Lua / Python)

Per plugin "leggeri" senza dover ricompilare. Tre opzioni con caratteristiche diverse:

### Rhai — Crate `rustre-script-rhai`
Linguaggio embedded scripting pure-Rust, no FFI, no dipendenze esterne, sandboxed by default, sintassi Rust-like. Migliore per scripting "leggero" inline a workflow + sicurezza first (no escape dalla sandbox senza unsafe explicit).

```rhai
fn on_function_analyzed(func) {
    if func.size > 1000 {
        func.add_comment(`Large function: ${func.name}`);
    }
}
rustre::events::on("function_analyzed", on_function_analyzed);

rustre::actions::register("my_action", "Tools/My Action", |ctx| {
    let addr = ctx.current_address();
    print(`Cursor at: ${addr:x}`);
});
```

Pro: zero deps, fast startup, easy embedding, sandbox restrictiva di default. Contro: piccola community, meno potente di Python.

### Lua — Crate `rustre-script-lua`
Via `mlua` con LuaJIT backend (più veloce di PUC-Rio Lua di ~10x). API esposta come tabella globale `rustre`.

```lua
function on_function_analyzed(func)
    if func:size() > 1000 then
        func:add_comment("Large function: " .. func:name())
    end
end
rustre.events.on("function_analyzed", on_function_analyzed)

rustre.actions.register("my_action", "Tools/My Action", function(ctx)
    local addr = ctx.current_address()
    print(string.format("Cursor at: 0x%x", addr))
end)
```

Pro: linguaggio piccolo, ottime performance LuaJIT, ampia knowledge nei reverse engineers (Wireshark, ZAP, IDA usano Lua).

### Python — Crate `rustre-script-python`
Via `pyo3` con cpython embedded. Per compatibilità con script IDAPython, Ghidra Python, Frida Python existing. Permette riuso enorme ecosystem Python (`pwntools`, `angr`, `capstone`, `unicorn`, ML libraries).

```python
import rustre

bv = rustre.current_binary()
for func in bv.functions:
    if func.name.startswith("aes_"):
        func.set_color("yellow")
        for caller in func.callers:
            print(f"Crypto function called by {caller.name} at {caller.address:x}")
```

Pro: maturity, ecosystem, mainstream RE community. Contro: heavier (Python interpreter embedded ~30MB), GIL constraints, distribution complicated.

### API Surface
Trait `ScriptingBackend` astrae i tre. Ogni metodo esposto è disponibile in tutti e tre i linguaggi con conversioni di tipo automatiche:
```rust
pub trait ScriptingBackend {
    fn register_function<F: ScriptCallable>(&mut self, name: &str, f: F);
    fn eval(&mut self, code: &str) -> ScriptResult<ScriptValue>;
    fn load_file(&mut self, path: &Path) -> ScriptResult<()>;
    fn subscribe_event(&mut self, event: &str, handler: ScriptCallback);
}
```

User sceglie quale backend usare per ciascuno script via manifest header (`#!rustre:rhai`, `#!rustre:lua`, `#!rustre:python`) o estensione file (`.rh`, `.lua`, `.py`).

### 33.5 Plugin Marketplace

`~/.rustre/plugins/` directory con plugin installati. Manifest centralizzato `plugins.toml`. CLI:
- `rustre plugin install <name>`
- `rustre plugin update`
- `rustre plugin list`
- `rustre plugin remove <name>`

Sorgenti: GitHub repos (con manifest `rustre.toml`), self-hosted registry, official curated index. GUI plugin manager in settings.

Security: signature verification, permission display al primo install, sandbox enforcement runtime.

### 33.6 Example Plugins (Reference / Tutorial)

Bundled o linkati nel registry ufficiale come esempi di come scrivere plugin reali. Servono anche come template iniziale per nuovi sviluppatori:

- **`pdf-malware-classifier`**: applica YARA rules + heuristics su PDF caricati, segnala oggetti sospetti come JavaScript, OpenAction, Launch, embedded SWF. Esempio di plugin che combina loader-callback + YARA + UI annotation.
- **`office-vba-deobfuscator`**: estrae VBA, individua pattern di obfuscation comuni (string concatenation con Chr(), array reverse, Base64), normalizza in pseudocode VBA leggibile. Esempio di pass deobfuscation custom.
- **`ebpf-program-analyzer`**: per ogni programma eBPF caricato, identifica section type, mappa helper calls usati, traccia map access patterns, emette report su context di attachment. Esempio di analisi domain-specific.
- **`packed-elf-unpacker`**: rileva packing comune (UPX, MEW, FSG) e fa unpack tramite Unicorn emulation + memory snapshot. Esempio di emu + memory dump in workflow.
- **`iot-firmware-extractor`**: ricostruisce filesystem da firmware dumps (squashfs, jffs2, ubifs, cramfs), estrae binary + config + certificates. Esempio di loader composto + extraction pipeline.
- **`mobile-permission-auditor`**: per APK/IPA, fa cross-reference tra permessi dichiarati e API effettivamente chiamate; segnala over-permissioning. Esempio di plugin che combina static + manifest analysis.
- **`crypto-constants-finder`**: scan del binary per costanti note di algoritmi crittografici (AES S-box, SHA constants, MD5 K, RC4 KSA pattern, Curve25519 base point) → annota le funzioni che le usano. Esempio classico di analisi pattern matching.
- **`api-hashing-resolver`**: malware spesso resolve API via hash invece di nome (per evadere detection). Plugin che, dato hashing algorithm noto (CRC32, FNV, custom rolling), pre-calcola hash di tutte le Windows API names e annota le costanti hash trovate nel binary con il nome API risolto. Esempio di analisi context-specific malware.
- **`license-key-extractor-generic`**: heuristic-based finder di license key validation routines (loop di character comparison, mod-arithmetic checks). Esempio di analisi pattern recognition + auto-annotation.

## 34. Knowledge Graph & Project Database — Dettaglio

### 34.1 Filosofia

Tutto ciò che l'utente o l'analisi producono è un fatto nel knowledge graph, ed è persistente. Il KG è il "single source of truth" del progetto. Nessuna view ha state proprio non-derivabile: rebuildare l'intera UI da zero deve essere possibile interrogando il KG.

Vantaggi:
- Sincronizzazione automatica tra views (cambia nome funzione in disassembly → si aggiorna ovunque)
- Time-travel del progetto (KG è versionato, posso vedere "stato del progetto 2 ore fa")
- Diff tra analisi (confronto vecchio/nuovo stato del progetto stesso, non solo binari)
- Query potenti (Cypher-like) per workflow e plugin
- Export/import portatile

### 34.2 Storage Backend

Due opzioni, configurabili per project:

### Opzione A: SQLite + Custom Schema (default)
File `.rustre-project/project.db`. Schema relazionale:

```sql
CREATE TABLE binaries (
    id INTEGER PRIMARY KEY,
    sha256 TEXT NOT NULL UNIQUE,
    path TEXT NOT NULL,
    format TEXT NOT NULL,
    arch TEXT NOT NULL,
    base_addr INTEGER,
    entry_point INTEGER,
    metadata JSON
);

CREATE TABLE functions (
    id INTEGER PRIMARY KEY,
    binary_id INTEGER NOT NULL REFERENCES binaries(id),
    address INTEGER NOT NULL,
    end_address INTEGER,
    name TEXT,
    prototype TEXT,
    calling_convention TEXT,
    is_library BOOLEAN,
    is_thunk BOOLEAN,
    confidence REAL,
    flags INTEGER,
    user_modified BOOLEAN DEFAULT FALSE,
    UNIQUE(binary_id, address)
);
CREATE INDEX idx_func_name ON functions(name);

CREATE TABLE basic_blocks (
    id INTEGER PRIMARY KEY,
    function_id INTEGER NOT NULL REFERENCES functions(id),
    start_addr INTEGER NOT NULL,
    end_addr INTEGER NOT NULL,
    UNIQUE(function_id, start_addr)
);

CREATE TABLE edges (
    id INTEGER PRIMARY KEY,
    from_bb_id INTEGER NOT NULL REFERENCES basic_blocks(id),
    to_bb_id INTEGER NOT NULL REFERENCES basic_blocks(id),
    edge_type TEXT NOT NULL  -- 'fallthrough', 'unconditional', 'true', 'false', 'switch', 'call'
);

CREATE TABLE xrefs (
    id INTEGER PRIMARY KEY,
    from_addr INTEGER NOT NULL,
    to_addr INTEGER NOT NULL,
    binary_id INTEGER NOT NULL REFERENCES binaries(id),
    xref_type TEXT NOT NULL,  -- 'code_call', 'code_jump', 'data_read', 'data_write', 'data_addr'
    UNIQUE(binary_id, from_addr, to_addr, xref_type)
);
CREATE INDEX idx_xref_to ON xrefs(binary_id, to_addr);
CREATE INDEX idx_xref_from ON xrefs(binary_id, from_addr);

CREATE TABLE symbols (
    id INTEGER PRIMARY KEY,
    binary_id INTEGER NOT NULL REFERENCES binaries(id),
    address INTEGER NOT NULL,
    name TEXT NOT NULL,
    source TEXT NOT NULL,  -- 'pdb', 'dwarf', 'export', 'user', 'flirt', 'ai_suggested'
    confidence REAL DEFAULT 1.0,
    namespace TEXT
);

CREATE TABLE types (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    definition JSON NOT NULL,
    source TEXT NOT NULL,
    UNIQUE(name)
);

CREATE TABLE variables (
    id INTEGER PRIMARY KEY,
    function_id INTEGER NOT NULL REFERENCES functions(id),
    location TEXT NOT NULL,  -- 'stack[-0x10]', 'reg[rax]', 'param[0]'
    name TEXT,
    type_id INTEGER REFERENCES types(id),
    user_named BOOLEAN DEFAULT FALSE
);

CREATE TABLE comments (
    id INTEGER PRIMARY KEY,
    binary_id INTEGER NOT NULL REFERENCES binaries(id),
    address INTEGER NOT NULL,
    text TEXT NOT NULL,
    author TEXT,
    ts INTEGER NOT NULL,
    UNIQUE(binary_id, address)
);

CREATE TABLE bookmarks (
    id INTEGER PRIMARY KEY,
    binary_id INTEGER NOT NULL REFERENCES binaries(id),
    address INTEGER NOT NULL,
    label TEXT,
    color TEXT,
    ts INTEGER NOT NULL
);

CREATE TABLE strings (
    id INTEGER PRIMARY KEY,
    binary_id INTEGER NOT NULL REFERENCES binaries(id),
    address INTEGER NOT NULL,
    length INTEGER NOT NULL,
    encoding TEXT NOT NULL,
    value TEXT NOT NULL,
    is_decoded BOOLEAN DEFAULT FALSE,
    source TEXT
);
CREATE VIRTUAL TABLE strings_fts USING fts5(value, content='strings', content_rowid='id');

CREATE TABLE annotations (
    id INTEGER PRIMARY KEY,
    entity_type TEXT NOT NULL,
    entity_id INTEGER NOT NULL,
    key TEXT NOT NULL,
    value JSON NOT NULL,
    UNIQUE(entity_type, entity_id, key)
);

CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    actor TEXT NOT NULL,  -- 'user', 'analysis', 'ai', 'plugin:<name>'
    payload JSON NOT NULL
);

CREATE TABLE undo_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    transaction_id TEXT NOT NULL,
    ts INTEGER NOT NULL,
    forward_sql TEXT NOT NULL,
    reverse_sql TEXT NOT NULL,
    description TEXT
);
```

### Opzione B: Embedded Graph DB
Per progetti molto grandi (firmware corpus, threat intel hunting): backend graph nativo. Opzioni:
- **Custom in Rust**: built on top of `redb` (transactional key-value), node/edge tables, indici LSM-style
- **TerminusDB embedded** se diventa disponibile
- **DuckDB** con extensions per graph (più SQL-friendly, ottimo per analytics)

Trait `KgBackend`:
```rust
pub trait KgBackend: Send + Sync {
    fn open(path: &Path) -> Result<Self> where Self: Sized;
    fn begin_tx(&self) -> Result<Box<dyn KgTransaction>>;
    fn query(&self, query: &Query) -> Result<QueryResult>;
    fn subscribe(&self, pattern: &SubscribePattern) -> EventStream;
}
```

Default SQLite; switching backend mediante config.

### 34.3 Query Language

Mini-DSL Cypher-like:
```
MATCH (f:Function {name: "main"})-[:CALLS]->(g:Function)
WHERE g.is_library = false
RETURN g.name, count(g)
ORDER BY count(g) DESC
LIMIT 10
```

Implementazione: parser PEG → AST → compilatore a SQL (per backend SQLite) o graph traversal nativo (per backend graph). Tabella di mapping fra elementi Cypher e schema relazionale.

Esposto via:
- MCP tool `kg.query`
- Plugin API
- Console REPL nella GUI (bottom panel "KG Console")
- Workflow steps (`tool: kg.query`)

### 34.4 Event Bus & Reactivity

Tutte le mutazioni del KG generano eventi su un canale tokio:
```rust
pub enum KgEvent {
    FunctionAdded { binary_id: BinaryId, addr: Address },
    FunctionRenamed { binary_id: BinaryId, addr: Address, old: String, new: String },
    TypeChanged { binary_id: BinaryId, var_ref: VarRef, type_id: TypeId },
    CommentAdded { binary_id: BinaryId, addr: Address, text: String },
    BookmarkAdded { ... },
    // ... un evento per ogni tipo di mutazione
}
```

Views si abbonano agli eventi rilevanti (`KgSubscription::for_binary(binary_id)`) e re-render selettivo. AI conversation memory traccia eventi per "ricordare cosa è successo" senza re-query. Plugin reagiscono a eventi (es. plugin che auto-runna analisi dopo `BinaryLoaded`).

### 34.5 Undo / Redo

Ogni transazione scrive entry in `undo_log` con SQL forward + reverse. Undo applica reverse, redo applica forward. Multiplayer-friendly (futuro): operational transform tra azioni concorrenti.

### 34.6 Project File Layout

```
my_analysis.rustre-project/
├── project.toml          # Project metadata + settings
├── project.db            # Main KG (SQLite)
├── binaries/
│   ├── <sha256>/
│   │   ├── original      # Original binary file
│   │   ├── metadata.json
│   │   └── notes.md      # User markdown notes
├── recordings/           # TTD recordings
├── sandbox_reports/      # Sandbox JSON reports
├── memory_dumps/         # Memory dump files
├── pcaps/               # Network captures
├── attachments/         # Arbitrary user files
├── workflows/           # Custom workflow YAMLs
├── prompts/             # Project-specific AI prompts
├── plugins.toml         # Project-required plugins
└── README.md            # Project documentation
```

Project è una directory: facile da zippare, commitare in git, condividere.

### 34.7 Versioning & Diff

Schema migration tra app versions: ogni release del software ha migration scripts in `crates/rustre-project/migrations/`. Apertura di project con schema vecchio → run migrations.

Project diff: confronto fra due stati del progetto stesso (es. analisi di t0 vs analisi di t1 sullo stesso binary): nomi cambiati, comment aggiunti, type updates. Visualizzato come "history view".

### 34.8 Multi-User (Futuro)

Sincronizzazione collaborativa: project DB su server centrale (Postgres+Citus), WebSocket per event broadcast, OT/CRDT per merge concorrente. Roadmap, non MVP.

- **Apache 2.0**: permissive, permette commercializzazione closed. Spesso scelto per ecosistemi.
- **Source-Available + Commercial**: free for personal/research, license commerciale per uso enterprise. Modello Elastic/Mongo recente.
- **Dual License**: Open source + commercial. Modello classico Qt, MySQL.

Considerazione pratica: l'**AGPL v3 + commercial license** (modello Sentry, GitLab, Mattermost) è una opzione efficace se il progetto vuole open source + sostenibilità economica. Permette open ecosystem, ma chi vuole usarlo dentro un prodotto closed paga licenza commerciale al mantainer. Alternative valide: pura GPL/AGPL (community-only), Apache 2.0 (maximally permissive), source-available custom (BSL 1.1 Business Source).

### 36.3 Pratiche di Sviluppo Mandatorie

- **Test golden corpus**: directory `test-corpus/` con binari noti (DIE corpus, malware samples sanitized, open-source compiled with known symbols). Ogni release runna analisi su tutti, snapshot di output, diff vs baseline — CI fail se regressione semantica.
- **Property-based testing**: `proptest` per i parser/disassembler/lifters. Genera random input strutturati, verifica invariants (roundtrip, idempotence).
- **Fuzzing**: i tuoi stessi fuzzer (sezione 19) li giri sui tuoi parser. `cargo fuzz` su loader_pe, loader_elf, dex, ecc.
- **No unsafe senza giustificazione scritta**: ogni `unsafe` block ha commento `// SAFETY:` che spiega l'invariante.
- **MSRV pin**: stable Rust più recente al momento del primo release, bump esplicito per breaking changes.
- **Documentation in code**: `#![warn(missing_docs)]` su crate publici.
- **Reproducible builds**: `Cargo.lock` committed, build environment documented (Nix flake?).
- **Hash della build**: ogni release ha hash di build attestato, signed releases.

### 36.4 Anti-Patterns da Evitare

- **Dio class central**: niente `App` god-object che sa di tutto. State distribuito in `Entity<T>` GPUI per view, KG per persistente.
- **Sync I/O nel render path**: tutto I/O async, view chiede dati ai actor in background, mostra spinner mentre attende.
- **String-typed APIs**: tipi forti ovunque. `Address(u64)` ≠ `u64`. Tagged unions per enum varianti, no string discriminator.
- **Plugin che usano API interne**: plugin DEVONO usare solo `rustre-plugin-api`. Se internal API leak, è bug → ridisegna API.
- **Macro-magic eccessiva**: derive macros sono ok, custom proc-macros più di 5-6 a livello workspace = overkill, complica debug.
- **Ottimizzazione prematura**: profila prima, ottimizza dopo. `cargo flamegraph` su workload reali. Bonus: integra `tracy` profiler per real-time profiling durante uso.

### 36.5 Sicurezza Operativa Della Suite Stessa

La suite analizza malware, quindi è essa stessa target. Hardening:
- **Sandbox di parsing**: i parser girano in subprocess separati con seccomp/AppContainer per default. Crash di un parser su input malformato non porta giù tutta l'app.
- **No execute by default**: aprire un file NON lo esegue. Esecuzione richiede esplicito "Run in Sandbox".
- **Path traversal hardening**: tutti i loader che leggono archivi (APK, JAR, IPA) sanificano path entries, no escape di output directory.
- **Memory mapping safety**: `mmap` di file untrusted con `MAP_PRIVATE`, no `MAP_SHARED`, accesso solo via bounds-checked wrapper.
- **Plugin permissions**: enforced. Manifest dichiara, runtime checka, deny default.
- **Telemetry opt-in**: zero telemetria default. Se utente abilita anonymous crash reports, vanno a server controllato dal mantainer del progetto con dati anonimizzati e schema documentato.
- **Update verification**: ogni update verificato con Ed25519 signature contro chiave pubblica hardcoded nel binary.

### 36.6 Posizionamento Strategico

Cosa rende RustRE diversa da IDA / Ghidra / Binary Ninja / radare2:

1. **Unificazione totale**: nessun altro tool unisce static + dynamic + TTD + mobile + memory forensics + sandbox + network + threat intel + AI in un unico workflow integrato. Workflow tipico oggi: IDA Pro + WinDbg + Frida + Volatility + Wireshark + ANY.RUN + MISP = 7 tool con context-switch continuo, formati di export incompatibili, KB sparpagliata. RustRE è UNA app con UN knowledge graph dove ogni artefatto è interconnesso.

2. **AI-native**: non un plugin AI aggiunto sopra (come Hex-Rays AI o Binary Ninja Sidekick), ma AI integrata in ogni view, con accesso completo a tutto via MCP. L'agente AI può eseguire static analysis, lanciare il debugger, parsare un pcap, query VirusTotal, scrivere uno YARA rule, e mettere tutto insieme in una sola conversazione.

3. **Rust performance**: GUI fluida su binari multi-GB, analisi pesantemente parallelizzata (rayon su passes embarrassingly-parallel), latency UI bassa anche durante analisi in background. Memory safety significa zero crash su input adversarial — fondamentale dato che la suite analizza malware deliberatamente malformato.

4. **MCP federato bidirezionale**: RustRE è simultaneamente client e server MCP. Chiamabile da qualunque AI agent (Claude Desktop, Cursor, custom orchestratori). Può a sua volta orchestrare strumenti esterni MCP-capable (Frida MCP, Ghidra MCP, threat intel MCP) in workflow ibridi.

5. **Open source con licensing pulito**: per security researcher, accademia, hobbyist. Modello dual-license per sostenibilità del progetto a lungo termine.

6. **Architettura plugin-first**: ogni componente è estendibile. Custom loaders, custom architectures, custom analysis passes, custom views — tutto via trait stable + scripting (Rhai/Lua/Python). Domini specifici (firmware IoT, ICS/SCADA, mobile-specific, malware family-specific) coperti via plugin senza toccare il core.

7. **Knowledge graph come single source of truth**: ogni fatto (function name, type, comment, xref, dynamic observation) è persistente, query-abile in SQL/Cypher-like, versionato, multi-binary, diff-abile tra stati del progetto. Niente altro tool ha questa coesione di state.

### 36.7 Modelli Di Sostenibilità

Per progetto open source di questa dimensione, sostenibilità economica non è opzionale. Tre angoli compatibili:

- **Open core + commercial license**: codebase open AGPL, ma licenza commerciale a pagamento per chi vuole usarla in prodotti closed-source o vuole supporto enterprise. Modello Sentry, GitLab, MongoDB. Funziona bene quando c'è clear separation tra "individui/community" e "enterprise"; valuable per security firms, gov contractors, consulting firms.
- **Service/support**: training, supporto prioritario, consulting su workflow custom, deploying private cloud instances con LLM hosted. Margins alti, scalabile con headcount.
- **AI training data & model**: la pipeline fine-tuning (sezione 31.7) produce modelli specializzati in RE. I model standalone hanno valore di vendita a security vendor che vogliono potenziare i loro tool senza costruire l'infrastruttura da zero. Subscription per accesso a model continuamente aggiornato.

Una sequenza naturale: tool free (open core) → costruisce community + brand → revenue commerciali (license + services) → expansion in modelli AI / model marketplace.

### 36.8 Realtà Brutale Da Non Dimenticare

- **La quality bar è alta**: utenti RE sono esperti, intolleranti a tool buggy. Una crash su input strano e perdono fiducia. Mantenere golden tests + fuzzing continuo + beta program serio sono non-negotiable.
- **Manutenzione vince sempre alla scrittura**: anno 2 dello sviluppo è quando si capisce se il design ha tenuto. Modularizzare aggressivamente, separare concerns, evitare coupling tight tra layer — l'investimento sull'architettura nel mese 1 paga 100x più avanti.
- **L'ego dello scope**: scope completo è ambizioso. Ma il rilascio deve essere graduale, non un megalitico v1.0 dopo 3 anni di silenzio. Public dogfooding precoce. Prima release "minimal viable", incrementale dopo.
- **Le specifiche dei competitor non sono insormontabili**: come confermato (sezione 0), la knowledge è in letteratura pubblica + codice open di rivali. Ma c'è un asintoto di qualità che richiede ricerca, non solo codifica. Hex-Rays C output dopo 30 anni è qualcosa che pochissimi raggiungono. Obiettivo realistico nei primi 18-24 mesi: qualità Ghidra/Binary Ninja media. Hex-Rays-tier è obiettivo di lungo termine.

### 36.9 Decisioni Tecniche Aperte

In ordine di urgenza decisionale:

1. **GPUI vs egui vs Iced**: GPUI è già scelto per questo progetto (Zed framework). Astrarre uno strato `UiBackend` trait sopra GPUI è prudente: se mai si dovesse switchare a egui per ragioni di stabilità, viste possono essere riportate senza riscrivere il core UI logic.

In parallelo, decompiler interno matura e quando supera Ghidra in metriche oggettive su corpus standard, switch del default.
4. **License**: AGPL + commercial dual è il default suggerito sopra. Decisione finale del mantainer.
5. **Branding del progetto**: "RustRE" è working name della codebase. Possibili evoluzioni: "RustRE", "ReverseSuite", brand più memorabile. Decisione di marketing, non tecnica, ma da fare prima del primo public release.
6. **Architettura di distribution**: singolo binario `rustre` (GUI) + `rustre-cli` (headless) + `rustre-daemon` (long-running MCP server) è il default. Alternative: suite di micro-tools stile Sysinternals, ognuno standalone. Default consigliato è il primo, più mainstream e più allineato all'UX di IDA/Binary Ninja.
7. **Bootstrap target**: prima feature da rilasciare pubblicamente — disassembly viewer PE/ELF x86_64 + analysis basic + GPUI shell? O headless server MCP + CLI? La risposta dipende dalla audience iniziale (researcher con UI vs automation engineers).

## 37. Advanced Adversarial Deobfuscation & Decryption Engine

Sezione dedicata alle tecniche avanzate per analizzare binari con protezioni multi-stadio: packing, virtualization, anti-debug/anti-VM, whitebox crypto, online activation, self-modifying code, e combinazioni di tutto quanto sopra. Le sezioni 11 (instrumentation), 12 (emulation), 13 (symbolic execution), 20 (deobfuscation base) coprono i building block; questa sezione li orchestrate in un sistema avversariale iterativo.

### 37.1 Filosofia — Iterative Adversarial Deobfuscation Loop (IADL)

Lo stato dell'arte negli RE tool tratta deobfuscation come problema *shot singolo*: carica il binario, esegui algoritmo, output. Funziona per protezioni semplici (UPX, packer banali, MBA isolato) e fallisce sistematicamente contro tutto il resto: protezioni multi-stadio, VM-based protection, code morphing, layer crittografici dinamici.

L'approccio corretto è trattare la deobfuscation come un **gioco avversariale iterativo** dove ogni iterazione raffina la comprensione del binario specifico. È esattamente cosa fa un reverser umano esperto manualmente nell'arco di settimane; automatizzarlo è il game-changer.

Loop principale:
```
[1] Snapshot stato corrente (binario + analisi parziale finora)
[2] Generate hypotheses sulla protezione applicata (N candidate, ranked by prior)
[3] Per ogni ipotesi: apply tentative deobfuscation pass (parallel)
[4] Esegui ogni candidato in sandbox/emulator/hardware-trace
[5] Score: code naturalness + behavior equivalence + complexity reduction
[6] Aggiorna confidence delle ipotesi, accetta/scarta
[7] Merge best candidates → nuovo stato baseline
[8] Goto [1] until fixpoint (no improvement) o time budget esaurito
```

Proprietà fondamentali:
- **Convergente**: ogni iterazione produce stato strictly meglio definito (o stesso, se nessuna ipotesi vince)
- **Multi-layer resilient**: protezioni multi-stadio vengono pelate uno alla volta naturalmente, senza richiedere conoscenza priori della loro composizione
- **Self-tuning per binario**: il tool impara su QUEL specifico target invece di applicare ricetta fissa
- **Parallelizzabile**: ogni hypothesis valutata in thread separato (rayon)
- **Auditable**: ogni step nel KG come transazione versionata, undoable, branchable (vedi sezione 34.5)
- **AI-guided ma deterministicamente verificato**: AI propone ipotesi, esecuzione concreta + scoring le verifica matematicamente

### 37.2 Crate `rustre-deobf-iadl` — Orchestrator

Architettura del loop:

```rust
pub struct IadlOrchestrator {
    state: IadlState,
    hypothesis_registry: HypothesisRegistry,
    scorers: Vec<Box<dyn Scorer>>,
    executors: Vec<Box<dyn HypothesisExecutor>>,
    budget: ResourceBudget,
    kg: Arc<KnowledgeGraph>,
}

pub struct IadlState {
    /// Working binary view (potentially virtually patched)
    pub view: BinaryView,
    /// Layers di protezione identificati finora (ordinati dal più esterno)
    pub identified_layers: Vec<ProtectionLayer>,
    /// Funzioni con confidence di decompilazione corrente
    pub function_confidence: HashMap<Address, f64>,
    /// Iteration counter
    pub iteration: u32,
    /// Score globale dello stato (monotonic non-decreasing nel loop)
    pub global_score: f64,
}

pub trait Hypothesis: Send + Sync {
    fn id(&self) -> HypothesisId;
    fn name(&self) -> &str;
    fn description(&self) -> String;
    /// Prior probability dato lo stato corrente (Bayesian)
    fn prior(&self, state: &IadlState) -> f64;
    /// Apply hypothesis to state (returns new tentative state, non-destructive)
    fn apply(&self, state: &IadlState) -> Result<TentativeState>;
    /// Cost stimato di valutazione (sec * CPU)
    fn estimated_cost(&self) -> Duration;
}

pub trait Scorer: Send + Sync {
    fn name(&self) -> &str;
    fn weight(&self) -> f64;
    /// Score: maggiore = meglio. Range tipico 0.0-1.0
    fn score(&self, tentative: &TentativeState, baseline: &IadlState) -> f64;
}

pub trait HypothesisExecutor: Send + Sync {
    /// Esegue il binario tentative e raccoglie behavior signal
    fn execute(&self, tentative: &TentativeState) -> Result<BehaviorTrace>;
}

impl IadlOrchestrator {
    pub async fn run(&mut self, max_iterations: u32) -> Result<IadlReport> {
        let mut report = IadlReport::new();
        for iter in 0..max_iterations {
            self.state.iteration = iter;
            
            // [1] Generate hypotheses
            let hypotheses = self.hypothesis_registry
                .generate_for_state(&self.state);
            
            // [2-4] Apply + execute + score (parallel)
            let results: Vec<EvalResult> = hypotheses
                .par_iter()
                .map(|hyp| self.evaluate_hypothesis(hyp.as_ref()))
                .collect::<Result<Vec<_>>>()?;
            
            // [5-6] Pick best
            let best = results.iter()
                .max_by(|a, b| a.score.total_cmp(&b.score));
            
            // [7] Merge if improvement
            match best {
                Some(eval) if eval.score > self.state.global_score => {
                    self.merge_into_state(eval)?;
                    report.add_iteration(iter, eval.clone());
                }
                _ => {
                    report.add_no_progress(iter);
                    // Fixpoint check: 3 iterations senza progresso → exit
                    if report.consecutive_no_progress() >= 3 {
                        break;
                    }
                }
            }
            
            // Budget check
            if self.budget.exhausted() {
                report.set_budget_exhausted();
                break;
            }
        }
        Ok(report)
    }
    
    fn evaluate_hypothesis(&self, hyp: &dyn Hypothesis) -> Result<EvalResult> {
        let tentative = hyp.apply(&self.state)?;
        let traces: Vec<BehaviorTrace> = self.executors.iter()
            .map(|e| e.execute(&tentative))
            .collect::<Result<Vec<_>>>()?;
        let scores: Vec<(f64, f64)> = self.scorers.iter()
            .map(|s| (s.score(&tentative, &self.state) * s.weight(), s.weight()))
            .collect();
        let total_weight: f64 = scores.iter().map(|(_, w)| w).sum();
        let weighted_score: f64 = scores.iter().map(|(s, _)| s).sum::<f64>() / total_weight;
        Ok(EvalResult {
            hypothesis_id: hyp.id(),
            score: weighted_score,
            tentative,
            traces,
        })
    }
}
```

### 37.3 Scoring Framework

Tre famiglie di scorer, weighted:

**a. Naturalness Scorer** (`weight: 0.4`): modello statistico di "quanto il codice decompilato sembra scritto da umani". Features estratte:
- Distribuzione dimensioni basic block (codice umano = log-normal, codice obfuscato = bimodale)
- Branching factor medio (umano ~1.8-2.2 successors/BB, obfuscato spesso 1.0 o >3)
- Lunghezza expression tree del decompiler (umano: median 3-7 nodes; CFF: median 12+)
- Ratio loop/conditional/sequential (umano ha mix bilanciato; protected ha skew)
- Distribuzione costanti (umano: many "0", "1", offset piccoli; obfuscato: random-looking)
- N-gram di pseudoistruzioni MLIL (modello trained su decompiled di Debian binaries con simboli)

Implementazione: gradient-boosted classifier (xgboost via bindings Rust o reimplementazione pura) addestrato su corpus di binari open source compilati senza obfuscazione, con feature extraction in `rustre-deobf-iadl::scoring::naturalness`.

**b. Behavior Equivalence Scorer** (`weight: 0.4`): verifica matematica che il candidato preservi semantica. Approcci composti:
- **Test vector replay**: emula original binary + candidato con N input vector (random + edge case + corpus xref). Output esattamente identici = score 1.0. Diff su qualche bit = score proporzionale.
- **Path coverage diff**: traccia path coverage (Lighthouse-style, sezione 18) di original vs candidato. Se i path coperti dai test sono identici → score 1.0.
- **Symbolic equivalence sui blocchi critici**: per BB di crypto/check funzioni, run SymEx su input simbolico, output simbolico = equivalente formale (Z3 verify).

**c. Complexity Reduction Scorer** (`weight: 0.2`): metrica oggettiva di "il codice è diventato più semplice". Features:
- Numero istruzioni totali (lower = better)
- Cyclomatic complexity (lower = better)
- Number of basic blocks (lower, ma non zero)
- Depth of CFG DAG (lower = better)
- Number of unique MLIL expression types (lower diversity = more uniform = often cleaner)

Score finale: weighted sum normalizzato + sanity check (non accettare candidati che riducono complexity a zero o sotto threshold).

### 37.4 Crate `rustre-crypto-id` — Active Crypto Identification

```rust
pub struct TestVectorDb {
    /// Test vector noti per ogni algoritmo standard
    vectors: HashMap<AlgorithmId, Vec<TestVector>>,
}

pub struct TestVector {
    algorithm: AlgorithmId,
    key: Option<Vec<u8>>,
    iv: Option<Vec<u8>>,
    plaintext: Vec<u8>,
    expected_ciphertext: Vec<u8>,
    source: String,  // "NIST AESAVS", "RFC 8439", etc.
}

impl CryptoIdentifier {
    pub fn identify(&self, candidate: &Function, view: &BinaryView) -> Vec<Identification> {
        let mut results = Vec::new();
        
        // Probe 1: entropy analysis on output
        let entropy = self.probe_entropy(candidate);
        let class = self.classify_by_entropy(entropy);  // cipher / hash / kdf / prng / unknown
        
        // Probe 2: avalanche characteristic
        let avalanche = self.probe_avalanche(candidate);
        // ~50% bit flip per input bit = good cipher; ~0% = unrelated; ~100% = bijective shift
        
        // Probe 3: test vector match
        for (algo, vectors) in self.test_vectors.iter_by_class(&class) {
            let mut matches = 0;
            for tv in vectors {
                if self.try_test_vector(candidate, tv).is_match() {
                    matches += 1;
                }
            }
            if matches >= 3 || (matches >= 1 && vectors.len() == 1) {
                results.push(Identification {
                    algorithm: algo.clone(),
                    confidence: matches as f64 / vectors.len() as f64,
                    method: IdMethod::TestVectorMatch,
                });
            }
        }
        
        // Probe 4: differential cryptanalysis
        let diff_profile = self.probe_differential(candidate);
        if let Some(algo) = self.fingerprint_db.match_diff_profile(&diff_profile) {
            results.push(Identification {
                algorithm: algo,
                confidence: diff_profile.confidence,
                method: IdMethod::DifferentialFingerprint,
            });
        }
        
        // Probe 5: block size detection (cipher only)
        if class == CryptoClass::Cipher {
            if let Some(block_size) = self.probe_block_size(candidate) {
                results.iter_mut().for_each(|r| {
                    if r.algorithm.expected_block_size() == Some(block_size) {
                        r.confidence *= 1.2;  // boost confidence
                    }
                });
            }
        }
        
        // Probe 6: key extraction (se algoritmo identificato + funzione prende key come arg)
        for ident in &mut results {
            if let Some(key) = self.try_extract_key(candidate, &ident.algorithm, view) {
                ident.extracted_key = Some(key);
            }
        }
        
        results
    }
    
    fn try_test_vector(&self, func: &Function, tv: &TestVector) -> TestResult {
        let mut emu = self.emulator.clone_fresh();
        emu.map_binary(func.binary());
        let key_addr = emu.alloc_and_write(&tv.key.clone().unwrap_or_default());
        let pt_addr = emu.alloc_and_write(&tv.plaintext);
        let out_addr = emu.alloc(tv.expected_ciphertext.len());
        emu.set_args(&[key_addr, pt_addr, out_addr, tv.plaintext.len() as u64]);
        emu.run_function(func.address(), Duration::from_secs(2))?;
        let actual = emu.read(out_addr, tv.expected_ciphertext.len())?;
        if actual == tv.expected_ciphertext {
            TestResult::Match
        } else if actual.iter().zip(&tv.expected_ciphertext).filter(|(a,b)| a == b).count() 
                  > tv.expected_ciphertext.len() / 2 {
            TestResult::PartialMatch
        } else {
            TestResult::NoMatch
        }
    }
    
    fn probe_avalanche(&self, func: &Function) -> AvalancheProfile {
        let mut profile = AvalancheProfile::default();
        let base_input = vec![0u8; 64];
        let base_output = self.emulate_output(func, &base_input);
        for bit_pos in 0..512 {
            let mut modified = base_input.clone();
            modified[bit_pos / 8] ^= 1 << (bit_pos % 8);
            let modified_output = self.emulate_output(func, &modified);
            let bit_flips = hamming_distance(&base_output, &modified_output);
            profile.flips_per_input_bit.push(bit_flips);
        }
        profile.compute_avg_and_variance();
        profile
    }
    
    fn try_extract_key(&self, func: &Function, algo: &AlgorithmId, view: &BinaryView) 
        -> Option<Vec<u8>> 
    {
        // Strategy 1: if function is called with constant key pointer, extract from data section
        for caller in func.callers() {
            let key_arg_addr = self.recover_arg_value(caller, algo.key_arg_index())?;
            if view.is_data_address(key_arg_addr) {
                let key_size = algo.expected_key_size();
                return Some(view.read(key_arg_addr, key_size).ok()?);
            }
        }
        // Strategy 2: if key is computed at runtime, run setup function symbolically + extract
        // (more complex, defer to SymEx)
        None
    }
}
```

### 37.5 Crate `rustre-deobf-smc` — Self-Modifying Code Reconstruction

Per binari packed multi-stadio o codice che decripta sé stesso, ricostruzione dell'unpacked stable form attraverso tracing instrumentato.

```rust
pub struct SmcReconstructor {
    backend: SmcBackend,
    timeline: CodeGenerationTimeline,
}

pub enum SmcBackend {
    Frida(FridaSession),       // instrumentation runtime
    Unicorn(UnicornEmu),       // emulation
    IntelPt(PtCapture),        // hardware trace
}

pub struct CodeGenerationTimeline {
    /// Eventi cronologici di scrittura su pagine executable
    events: Vec<WriteEvent>,
    /// Snapshot di pagine in punti chiave
    snapshots: Vec<PageSnapshot>,
}

pub struct WriteEvent {
    timestamp: u64,
    page_addr: Address,
    offset: usize,
    bytes: Vec<u8>,
    writer_pc: Address,  // istruzione che ha scritto
    thread_id: u32,
}

impl SmcReconstructor {
    pub fn reconstruct(&mut self, binary: &BinaryView, entry: Address) -> Result<UnpackedBinary> {
        // 1. Setup: identifica pagine inizialmente eseguibili + permessi
        let initial_exec_pages = binary.executable_pages();
        
        // 2. Hook tutte le write su quelle pagine (e su pagine che diventeranno X dopo mprotect)
        self.backend.hook_writes_to_x_pages()?;
        
        // 3. Hook tutte le mprotect/VirtualProtect che marcano pagine come X
        self.backend.hook_protect_to_x()?;
        
        // 4. Run binary fino a un trigger (es. main(), o un timeout, o un signal "ho finito unpack")
        self.backend.run_until_trigger(entry, UnpackTrigger::HeuristicStable)?;
        
        // 5. Costruisci timeline dagli eventi catturati
        self.timeline = self.backend.collect_timeline();
        
        // 6. Identifica stage boundaries
        let stages = self.identify_stages();
        
        // 7. Snapshot finale = ultimo stage stable
        let final_snapshot = stages.last().unwrap().snapshot.clone();
        
        // 8. Genera unpacked binary
        let unpacked = self.build_unpacked_binary(binary, &final_snapshot)?;
        
        Ok(unpacked)
    }
    
    fn identify_stages(&self) -> Vec<UnpackStage> {
        let mut stages = Vec::new();
        let mut current_writes = Vec::new();
        let mut last_write_ts = 0u64;
        
        for event in &self.timeline.events {
            // Stage boundary: gap temporale significativo + transizione a control flow
            // in pagina diversa
            if event.timestamp - last_write_ts > STAGE_GAP_NS 
               && !current_writes.is_empty() 
            {
                stages.push(UnpackStage {
                    writes: std::mem::take(&mut current_writes),
                    snapshot: self.snapshot_at(last_write_ts),
                });
            }
            current_writes.push(event.clone());
            last_write_ts = event.timestamp;
        }
        
        if !current_writes.is_empty() {
            stages.push(UnpackStage {
                writes: current_writes,
                snapshot: self.snapshot_at(last_write_ts),
            });
        }
        
        stages
    }
    
    fn build_unpacked_binary(&self, original: &BinaryView, snapshot: &PageSnapshot) 
        -> Result<UnpackedBinary> 
    {
        // Costruisci nuovo PE/ELF con sections dal snapshot, headers fixed
        let mut builder = UnpackedBinaryBuilder::new(original.format());
        builder.set_arch(original.arch());
        builder.set_base_addr(snapshot.base_addr);
        builder.set_entry_point(snapshot.original_entry_in_snapshot()?);
        
        for region in snapshot.regions() {
            builder.add_section(Section {
                name: region.name.clone(),
                addr: region.addr,
                data: region.bytes.clone(),
                perms: region.perms,
            });
        }
        
        // Imports: ricostruisci IAT (Scylla-style)
        let iat_rebuild = ScyllaStyleIatRebuild::new(snapshot);
        let imports = iat_rebuild.rebuild()?;
        builder.set_imports(imports);
        
        // Annota nel KG la genealogia: questa unpacked binary deriva da quale original + via quale stage
        self.kg.add_unpack_genealogy(original.id(), &builder.preview_id(), &self.timeline);
        
        builder.build()
    }
}
```

Output: produce un binario unpacked stabile che può essere caricato come BinaryView normale e analizzato con tutto il resto del tool. Sezioni 15.5 (Scylla IAT rebuild) integrate qui.

### 37.6 Crate `rustre-deobf-mhcde` — Multi-Hypothesis Concurrent Deobfuscation Engine

Estensione di sezione 20 con orchestrazione concurrent di multiple deobf strategies + per-function scoring + best-pick.

```rust
pub struct Mhcde {
    passes: Vec<Box<dyn DeobfPass>>,
    scorer: Arc<dyn Scorer>,
    thread_pool: rayon::ThreadPool,
}

impl Mhcde {
    pub fn deobfuscate_function(&self, func: &MlilFunction) -> DeobfResult {
        // Run ogni pass in parallelo, ognuno su clone independent
        let candidates: Vec<CandidateOutput> = self.passes.par_iter()
            .filter(|p| p.applies_to(func))
            .map(|p| {
                let mut clone = func.deep_clone();
                let result = p.run(&mut clone, &mut PassContext::new());
                CandidateOutput {
                    pass_name: p.name().to_string(),
                    output: clone,
                    pass_result: result,
                }
            })
            .collect();
        
        // Scorer evaluates each candidate
        let scored: Vec<(CandidateOutput, f64)> = candidates.into_iter()
            .map(|c| {
                let score = self.scorer.score_candidate(&c.output, func);
                (c, score)
            })
            .collect();
        
        // Pick best
        let best = scored.into_iter()
            .max_by(|a, b| a.1.total_cmp(&b.1))
            .unwrap();
        
        DeobfResult {
            chosen_pass: best.0.pass_name,
            score: best.1,
            output: best.0.output,
            alternatives_considered: candidates.len(),
        }
    }
    
    /// Per binari interi: applica MHCDE per-function in parallel
    pub fn deobfuscate_binary(&self, view: &mut BinaryView) -> BinaryDeobfReport {
        let functions: Vec<MlilFunction> = view.functions().collect();
        let results: Vec<DeobfResult> = functions.par_iter()
            .map(|f| self.deobfuscate_function(f))
            .collect();
        // Merge back into view
        for (orig, result) in functions.iter().zip(&results) {
            view.replace_mlil(orig.address(), result.output.clone());
        }
        BinaryDeobfReport::from_results(results)
    }
}
```

Passes runnati in parallelo includono tutti quelli di sezione 20 (CFF removal, opaque predicates, MBA simplification, string deobf, VM deobf) più nuovi:
- **AI pattern match pass**: AI model trained su (obfuscated → cleaned) pairs; quando vede pattern noti, suggerisce trasformazione
- **Trace-based simplification**: usa execution trace per identificare quali branch sono mai-presi, dead code, simplification context-aware
- **Synthesizer pass**: per espressioni complesse, prova a *sintetizzare* espressione equivalente più semplice usando program synthesis (CEGIS-style — grammar-guided + Z3 verification)

Vince per ogni funzione il candidato col score migliore. Funzioni diverse possono essere best-deobfuscate da pass diversi: granularità per-funzione, non per-binario. Questo è fondamentale perché in un binario reale layer di protezione possono essere applicati selettivamente solo ad alcune funzioni critiche.

### 37.7 Crate `rustre-deobf-vmlift` — VM Bytecode Auto-Lifter

Estensione di sezione 20.6 con pipeline completa per defeating VM-based protection (VMProtect, Themida virtualization, Tigress VM, custom protector VMs). Stato dell'arte accademico: VMAttack (CC 2017), "Synthesis of Adversarial DNNs" research, paper Quarkslab su Tigress challenges.

```rust
pub struct VmLifter {
    dispatcher_detector: DispatcherDetector,
    handler_semantic_inferrer: HandlerSemanticInferrer,
    isa_synthesizer: VmIsaSynthesizer,
}

pub struct DispatcherDetector;

impl DispatcherDetector {
    pub fn find(&self, view: &BinaryView) -> Vec<VmDispatcher> {
        let mut results = Vec::new();
        for func in view.functions() {
            // Fingerprint 1: large switch (CFG con un nodo dominator + N successors uniform)
            if self.is_switch_dispatcher(func) {
                results.push(VmDispatcher {
                    address: func.address(),
                    handlers: self.extract_switch_handlers(func),
                    kind: DispatcherKind::SwitchBased,
                });
                continue;
            }
            // Fingerprint 2: computed jump via handler table
            if self.is_jump_table_dispatcher(func) {
                results.push(VmDispatcher {
                    address: func.address(),
                    handlers: self.extract_table_handlers(func),
                    kind: DispatcherKind::JumpTable,
                });
                continue;
            }
            // Fingerprint 3: threaded code (handler ends jumps directly to next handler)
            if self.is_threaded_dispatcher(func) {
                results.push(VmDispatcher {
                    address: func.address(),
                    handlers: self.extract_threaded_handlers(func),
                    kind: DispatcherKind::ThreadedCode,
                });
            }
        }
        results
    }
}

pub struct HandlerSemanticInferrer {
    symex: SymbolicEngine,
}

impl HandlerSemanticInferrer {
    pub fn infer(&self, handler: &Function, dispatcher_ctx: &VmDispatcher) 
        -> Result<HandlerSemantic> 
    {
        // Run handler symbolically con VM context simbolico:
        // - VM stack pointer simbolico
        // - VM registers simbolici
        // - bytecode pointer simbolico
        let mut state = self.symex.fresh_state();
        state.set_vm_context(VmContextSym::default());
        
        // Esegui finché handler ritorna (jump to dispatcher)
        let final_state = self.symex.execute_until_dispatcher_return(state, handler.address())?;
        
        // Analizza diff input vs output:
        // - VM stack modificato come?
        // - VM registers modificati come?
        // - bytecode pointer avanzato di quanto?
        // - memory access patterns?
        let semantic = HandlerSemantic {
            opcode: self.guess_opcode_from_dispatcher_branch(handler, dispatcher_ctx),
            stack_effect: self.diff_stack(&final_state, &state),
            register_effect: self.diff_registers(&final_state, &state),
            bytecode_advance: self.compute_bytecode_advance(&final_state, &state),
            memory_accesses: self.collect_memory_ops(&final_state),
            description: String::new(),  // filled by AI labeller
        };
        
        Ok(semantic)
    }
}

pub struct VmIsaSynthesizer;

impl VmIsaSynthesizer {
    pub fn synthesize(&self, handlers: &[(u32, HandlerSemantic)]) -> VmIsa {
        let mut isa = VmIsa::new();
        for (opcode, sem) in handlers {
            // Mappa semantica a LLIL operations
            let lift_template = self.semantic_to_llil_template(sem);
            isa.add_instruction(VmInstructionDef {
                opcode: *opcode,
                mnemonic: self.suggest_mnemonic(sem),
                operands: self.infer_operands(sem),
                semantic: lift_template,
            });
        }
        isa
    }
    
    fn semantic_to_llil_template(&self, sem: &HandlerSemantic) -> LlilTemplate {
        // Per ogni stack effect / register effect, genera LLIL equivalente
        // Esempio: "pop 2, push sum" → LLIL_PUSH(LLIL_ADD(LLIL_POP, LLIL_POP))
        // Pattern matching su forme canoniche conosciute, fallback a generic
        match sem.classify() {
            HandlerClass::StackBinop(op) => 
                LlilTemplate::push_binop(op, LlilTemplate::pop(), LlilTemplate::pop()),
            HandlerClass::LoadConst => 
                LlilTemplate::push(LlilTemplate::read_bytecode_imm(sem.imm_size())),
            HandlerClass::Load(size) => 
                LlilTemplate::push(LlilTemplate::load(size, LlilTemplate::pop())),
            HandlerClass::Store(size) => 
                LlilTemplate::store(size, LlilTemplate::pop(), LlilTemplate::pop()),
            HandlerClass::Branch => 
                LlilTemplate::cond_branch(LlilTemplate::pop(), 
                                          LlilTemplate::read_bytecode_imm(4)),
            _ => LlilTemplate::opaque_call(sem.id()),  // semantica complessa → black box callable
        }
    }
}

pub struct VmLifterPipeline;

impl VmLifterPipeline {
    pub fn full_pipeline(&self, view: &mut BinaryView) -> Result<VmLiftReport> {
        let detector = DispatcherDetector;
        let dispatchers = detector.find(view);
        
        let mut all_lifted = Vec::new();
        for disp in dispatchers {
            // Inferisci semantica di ogni handler
            let inferrer = HandlerSemanticInferrer::new();
            let semantics: Vec<(u32, HandlerSemantic)> = disp.handlers.iter()
                .enumerate()
                .map(|(opcode, h)| {
                    let sem = inferrer.infer(h, &disp)?;
                    Ok::<_, Error>((opcode as u32, sem))
                })
                .collect::<Result<_>>()?;
            
            // Sintetizza ISA della VM
            let synth = VmIsaSynthesizer;
            let isa = synth.synthesize(&semantics);
            
            // Identifica bytecode region
            let bytecode_region = self.find_bytecode_region(view, &disp)?;
            
            // Disassembla bytecode con quella ISA
            let vm_instructions = isa.disassemble(&bytecode_region);
            
            // Lift VM instructions a LLIL standard
            let lifted = isa.lift_to_llil(&vm_instructions);
            
            // Crea function "virtuale" nel BinaryView che rappresenta il codice VM-lifted
            let virt_addr = view.allocate_virtual_function_address();
            view.insert_lifted_function(virt_addr, lifted, FunctionOrigin::VmLifted(disp.address));
            
            all_lifted.push(VmLiftEntry {
                dispatcher: disp.address,
                virtual_function: virt_addr,
                num_handlers: semantics.len(),
                num_instructions_lifted: vm_instructions.len(),
            });
        }
        
        Ok(VmLiftReport { entries: all_lifted })
    }
}
```

Limitazioni oneste: funziona ottimamente su VM "semplici" (~80% delle VM custom amatoriali, Tigress VM, alcune protezioni game). Su VMProtect 3.x con thousands di handler heterogeneous e instructions semantically-overlapping, copertura iniziale 40-60%, fixpoint a 80-85% raggiungibile con tuning manuale. Non si vince sempre, ma si vince più di tutti i tool concorrenti.

```rust
pub struct DfaAttack {
    fault_strategy: FaultStrategy,
    statistical_analyzer: StatisticalAnalyzer,
}

impl WhiteboxAttack for DfaAttack {
    fn name(&self) -> &str { "DFA on Whitebox AES" }
    fn paper_reference(&self) -> &str { 
        "Bos et al., 'Differential Computation Analysis: Hiding Your White-Box Designs is Not Enough', CHES 2016"
    }
    
    fn run(&self, target: &WhiteboxTarget) -> Result<AttackResult> {
        let mut emu = UnicornEmu::new(target.arch())?;
        emu.map_binary(target.binary())?;
        
        // Collect N pairs of (faulted_input, faulted_output)
        let mut faulted_pairs: Vec<FaultedPair> = Vec::new();
        let n_faults = 100;
        
        for _ in 0..n_faults {
            let mut session = emu.clone_session();
            let input = random_plaintext_block();
            
            // Inject fault: durante esecuzione del round 8 o 9 (penultimo/ultimo round AES)
            session.set_fault_hook(target.last_round_addr(), 
                                   FaultType::SingleBitFlip);
            
            let output = session.execute_whitebox(target.entry(), &input)?;
            faulted_pairs.push(FaultedPair { input, output });
        }
        
        // Collect also clean pairs (no fault)
        let clean_pairs: Vec<CleanPair> = (0..n_faults)
            .map(|_| {
                let input = random_plaintext_block();
                let output = emu.execute_whitebox(target.entry(), &input)?;
                Ok(CleanPair { input, output })
            })
            .collect::<Result<_>>()?;
        
        // Statistical analysis: from diff (clean - faulted) outputs, recover last round key
        let last_round_key = self.statistical_analyzer
            .recover_last_round_key(&clean_pairs, &faulted_pairs)?;
        
        // From last round key, derive master AES key via key schedule reverse
        let master_key = aes_key_schedule_reverse(&last_round_key)?;
        
        Ok(AttackResult {
            success: true,
            recovered_key: Some(master_key),
            confidence: 0.95,
            method: "DFA via single-bit fault injection + statistical correlation".into(),
        })
    }
```

### 37.9 Crate `rustre-trace-pt` — Intel Processor Trace Integration

### 37.10 Crate `rustre-deobf-antianti` — Universal Anti-Anti-Debug Engine

Tutte le classi note di anti-debug attaccate sistematicamente da bypass appropriato per ogni classe. // Esempio di un bypasser
```rust
pub struct PebBeingDebuggedBypasser;

impl Bypasser for PebBeingDebuggedBypasser {
    fn class(&self) -> AntiDebugClass { AntiDebugClass::PebBeingDebugged }
    
    fn apply(&self, site: &DetectionSite, instr: &mut Instrumenter) -> Result<BypassApplied> {
        // Site = istruzione che legge PEB.BeingDebugged
        // Strategia: hook l'accesso, return 0 indipendentemente da valore reale
        // Su x64: PEB at GS:[0x60], BeingDebugged at offset 2
        // Hook al PC della read, sostituisce result register con 0
        let hook = instr.add_instruction_hook(site.address, |ctx| {
            // Identifica il register target della read (di solito eax dopo movzx)
            let target_reg = analyze_read_target(&ctx.instruction);
            ctx.set_register(target_reg, 0);
            ctx.skip_instruction();
        })?;
        Ok(BypassApplied { 
            class: self.class(), 
            hook_id: hook, 
            description: "PEB.BeingDebugged read forced to 0".into() 
        })
    }
}

pub struct RdtscDifferentialBypasser {
    fake_clock: Arc<Mutex<u64>>,
}

impl Bypasser for RdtscDifferentialBypasser {
    fn class(&self) -> AntiDebugClass { AntiDebugClass::RdtscDifferential }
    
    fn apply(&self, site: &DetectionSite, instr: &mut Instrumenter) -> Result<BypassApplied> {
        // Strategia: hook RDTSC, restituisce timer falso che progredisce *coerentemente* 
        // (linearmente proporzionale alle istruzioni eseguite, non al wall-clock)
        let clock = self.fake_clock.clone();
        let hook = instr.add_rdtsc_hook(move |ctx| {
            let mut c = clock.lock().unwrap();
            *c += FAKE_TICKS_PER_INSTRUCTION;
            ctx.set_rdtsc_result(*c);
        })?;
        Ok(BypassApplied { /* ... */ })
    }
}

impl AntiAntiDebugEngine {
    /// Pipeline completa: detect tutto + apply tutti i bypass
    pub fn disable_all(&self, view: &BinaryView, runtime: &mut RuntimeMonitor) 
        -> Result<DisableReport> 
    {
        let mut all_sites = Vec::new();
        
        // Static phase
        for detector in &self.detectors {
            all_sites.extend(detector.detect_static(view));
        }
        
        // Dynamic phase (more accurate but requires execution)
        for detector in &self.detectors {
            all_sites.extend(detector.detect_dynamic(runtime));
        }
        
        // Dedup + sort by classe
        let unique_sites: Vec<DetectionSite> = dedup_by_addr_class(all_sites);
        
        let mut applied = Vec::new();
        for site in &unique_sites {
            if let Some(bypasser) = self.bypassers.get(&site.class) {
                match bypasser.apply(site, &mut self.instrumenter) {
                    Ok(b) => applied.push(b),
                    Err(e) => warn!("Bypass failed for {:?}: {}", site.class, e),
                }
            } else {
                warn!("No bypasser registered for class {:?}", site.class);
            }
        }
        
        Ok(DisableReport {
            total_detected: unique_sites.len(),
            total_bypassed: applied.len(),
            applied,
            unhandled: unique_sites.len() - applied.len(),
        })
    }
}
```

### 37.11 Crate `rustre-crypto-oracle` — Online Decryption Oracle Discovery

Per binari che richiedono materiale crittografico ottenuto runtime (license activation, DRM key exchange, cloud-validated authentication, C2 protocol per malware).

```rust
pub struct OracleDiscovery {
    mitm: Arc<MitmProxy>,            // sezione 21.4
    instrumenter: Arc<Instrumenter>, // sezione 11
    protocol_synthesizer: ProtocolSynthesizer,
}

impl OracleDiscovery {
    pub fn discover(&mut self, binary: &BinaryView) -> Result<OracleProtocol> {
        // 1. Avvia binary sotto instrumenter + MITM proxy
        let session = self.launch_under_observation(binary)?;
        
        // 2. Wait per network activity correlated con activation/decryption flow
        // Heuristic: prima request HTTP/HTTPS prima del primo accesso a crypto function
        let activation_request = session.wait_for_activation_request(Duration::from_secs(60))?;
        
        // 3. Cattura request fingerprint
        let request_fingerprint = self.fingerprint_request(&activation_request);
        // Fingerprint includes: URL, method, headers, body structure (fields tipizzati)
        
        // 4. Cattura response e identifica come viene usata
        let response = activation_request.response();
        let response_usage = session.trace_response_usage(&response)?;
        // Trace shows: response bytes flow into which functions, used as input to which crypto ops
        
        // 5. Modifica fingerprint + replay → osserva behavior
        let mut perturbations = self.perturb_request(&request_fingerprint, 50);
        let mut behaviors = Vec::new();
        for perturbed in &perturbations {
            let response_p = self.mitm.replay_with(perturbed)?;
            let behavior = session.observe_response_handling(&response_p)?;
            behaviors.push((perturbed.clone(), behavior));
        }
        
        // 6. Sintetizza protocollo da observations
        let protocol = self.protocol_synthesizer.synthesize(
            &request_fingerprint,
            &response,
            &behaviors,
            &response_usage,
        )?;
        
        // 7. Genera local oracle che emula server
        let oracle = LocalOracle::from_protocol(protocol.clone())?;
        
        // 8. Verify: re-run binary con local oracle al posto del server, vedere se funziona
        let verification = self.verify_local_oracle(binary, &oracle)?;
        
        Ok(OracleProtocol {
            protocol,
            local_oracle: oracle,
            verification,
        })
    }
}

pub struct ProtocolSynthesizer {
    field_inferrer: FieldInferrer,
}

impl ProtocolSynthesizer {
    fn synthesize(&self, req: &Fingerprint, resp: &Response, 
                  behaviors: &[(Fingerprint, Behavior)], usage: &ResponseUsage) 
        -> Result<Protocol> 
    {
        let mut proto = Protocol::new();
        
        // Field type inference: ogni campo del request è statico, derived, o random?
        for field in req.fields() {
            let kind = self.field_inferrer.classify(field, behaviors);
            proto.add_request_field(field.name(), kind);
        }
        
        // Response field semantics
        for field in resp.fields() {
            let role = match usage.field_destination(field.name()) {
                Some(Destination::CryptoKey) => ResponseFieldRole::CryptoKey,
                Some(Destination::Validation) => ResponseFieldRole::ValidationToken,
                Some(Destination::EncryptedBlob) => ResponseFieldRole::Payload,
                None => ResponseFieldRole::Unused,
            };
            proto.add_response_field(field.name(), role);
        }
        
        // Computation: response[X] = f(request[Y])?
        // Tenta sintesi: per ogni response field, prova relazioni con request fields
        for resp_field in resp.fields() {
            if let Some(relation) = self.synthesize_relation(resp_field, &req, behaviors) {
                proto.add_relation(resp_field.name(), relation);
            }
        }
        
        Ok(proto)
    }
}

pub struct LocalOracle {
    protocol: Protocol,
    runtime: OracleRuntime,
}

impl LocalOracle {
    /// Start oracle as local HTTP server, intercept binary's requests
    pub fn start_local(&self, bind: SocketAddr) -> Result<OracleServer> {
        let server = OracleServer::bind(bind)?;
        let protocol = self.protocol.clone();
        server.set_handler(move |req| {
            let resp = protocol.compute_response(&req);
            Ok(resp)
        });
        server.run_in_background();
        Ok(server)
    }
    
    /// Export oracle as standalone script (Python/Rust)
    pub fn export_script(&self, lang: ScriptLang) -> Result<String> {
        match lang {
            ScriptLang::Python => self.protocol.to_python_oracle(),
            ScriptLang::Rust => self.protocol.to_rust_oracle(),
        }
    }
}
```

Output: oracle Python o Rust standalone che, runnando localmente sulla porta dove il binary si aspetta il server, fornisce response valide. Bypassa attivazione online senza modificare il binary stesso (utile per debugging/analysis legittima dove modificare il binary romperebbe altre cose).

**Posizionamento etico/legale**: feature opt-in con disclaimer chiaro. Configurabile come "Research mode" con logging audit di ogni uso. Use case legittimi includono: malware C2 protocol reconstruction (security research), legacy software che non può più contattare il server originale (compatibility), educational, red-team operations autorizzate. Use case in giurisdizioni dove DMCA-style laws si applicano: responsabilità dell'utente finale, disclaimer presente al primo avvio della feature.

### 37.13 Considerazioni Oneste

Quello che funziona bene (alta confidence di delivery in 18-24 mesi sviluppo):
- IADL framework + scoring (engineering pulito su fondamenta esistenti)
- Active crypto identification (database + emulation = solved problem)
- Self-modifying code reconstruction (Frida + tracing pattern noto, integrazione nuova)
- MHCDE multi-pass orchestration (parallel orchestration di pass esistenti)
- Universal anti-anti-debug (database di pattern + bypass per pattern noto)
- Intel PT integration (libipt esiste, integrazione è infra work)

Quello che funziona parzialmente (60-80% successo iniziale, miglioramento progressivo nel tempo):
- VM bytecode auto-lifter (eccellente su VM semplici/medie, lotta con VMProtect 3.x heavily-tuned)
- Whitebox crypto attacks (DFA è solved; BGE/DCA richiedono tuning per implementations specifiche)
- Online oracle discovery (funziona per protocolli "ben strutturati"; protocolli con randomness server-controlled o crypto challenge-response complex richiedono human input)

Quello che è ricerca attiva (delivery 3-5 anni con quality crescente):
- Naturalness model trained su corpus diverse (richiede training data + tuning continuo)
- Synthesis-based deobfuscation (program synthesis con grammar guided + Z3, area di ricerca attiva)
- ARM CoreSight integration (vendor fragmentation rende portability difficult)

Quello che potrebbe non essere raggiungibile da single developer (anche con AI):
- Defeating fully hardened whitebox AES con multiple external encodings (paper-level research)
- Complete VM lift per VMProtect 3.x quando hyper-tuned per ogni binary (arms race attivo con Oreans Technologies)
- Stealth deobfuscation che evade detection da watchdog Themida custom (richiede driver kernel-mode + arms race continua)

Per questi ultimi, strategia consigliata: lascia hooks nel design + plugin extension points + community contribution + offerta di servizi consulting per casi enterprise specifici. Non promettere capability che non puoi mantenere; promettere il framework + ammettere honestly che i casi più hard richiedono expertise human-in-the-loop.
